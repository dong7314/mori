### 2026-09-21 인프라 선행 검증과 다음 백엔드 작업

Knative Serving/Kourier 설치 및 테스트 앱의 1→0→1·응답을 확인했다. 이는 새로운 Mori API나 Hermes Adapter가 구현됐다는 뜻은 아니다. [실제 검증 기록](../architecture/knative-validation-2026-09-21.md).

최신 사용자 출력에서 `mori` namespace가 없음을 확인했다. 준비 명령을 안내했지만 사용자는 집에서 진행할 예정이므로 모델 ID 조회·Secret 생성·Hermes 배포를 완료로 표시하지 않는다. [정확한 재개 지점과 명령](../architecture/hermes-shared-resume.md).

다음 순서는 실제 Hermes↔기존 llama.cpp 단일 요청, SearXNG 검색 도구 검증, Hermes Knative 전환과 home 보존, 인증된 Mori Adapter와 `parking.save`/`parking.latest` 도구 연결이다. 검색은 주차 도구의 필수 의존성은 아니다. 기존 주차 서비스의 소유권·멱등성을 재사용한다. 입력 “지하 2층 C구역 C36에 주차했어”가 계정별 DB에 저장되고 이후 질문으로 조회되는 것을 첫 제품 인수 기준으로 한다. 에이전트는 여러 차례 LLM·도구 호출을 수행할 수 있으며, 사용자/작업 권한은 모델 인자가 아니라 서버 인증 문맥에서 주입한다.

짧은 내부 Hermes 호출은 완료까지 HTTP 연결을 유지하며 검증한다. 앱의 작업 접수·상태 조회와 영속 작업 처리는 이 통합 단계에서 구현하고, HTTP 종료 뒤 Pod 안에만 남은 백그라운드 작업을 제품 기능으로 제공하지 않는다. STT·캘린더·예약·파일 작업·Pro 전용 runtime은 이 첫 흐름 이후에 확장한다.

## 2. 데이터의 종류

| 종류 | 예시 | 보관·사용 방식 |
| --- | --- | --- |
| 사실 기록 | “9월 15일 오후 8:42, 지하 3층 B12에 주차” | 구조화된 DB 기록. 최신과 과거를 구분하고 사용자가 정정할 수 있다. |
| 사용자 선호 | “평일 7시 30분에 주차 위치를 확인하는 편” | 관찰 근거와 명시적 설정을 구분한다. 명시적 설정을 우선한다. |
| 자동화 규칙 | “평일 7시 30분, 최신 주차 위치를 표시” | 시간대·조건·대상·활성 상태를 갖는 실행 규칙 |
| 스킬 | “주차 발화에서 층·구역을 저장하고 출근 때 최신 기록 조회” | 재사용 절차, 필요한 도구, 버전, 검증 상태 |
| 대화·작업 이력 | 사용자의 요청과 처리 결과 | 맥락 연결과 문제 확인에 사용. 제품 기록을 대신하지 않는다. |

오늘의 주차 위치를 스킬 코드에 고정하지 않는다. 스킬은 실행 때 최신 기록을 조회하는 방법을 담는다. 개인화는 우선 기억과 절차의 개선을 뜻하며, 사용자별 모델 파인튜닝이나 LoRA 학습은 초기 범위에 넣지 않는다.

제품에서 조회·수정하는 일정과 기록의 기준은 PostgreSQL이다. Hermes 메모리는 필요한 요약·선호·스킬을 담는다. 정정·삭제 이벤트가 Hermes 상태에도 반영되도록 동기화 작업을 두고, 실행 직전 중요한 사실은 도구로 다시 읽게 한다. runtime이 쉬는 동안 발생한 정정·삭제는 버전 있는 동기화 작업으로 남기고 다음 dispatch 전에 반영한다. 동기화 실패 때 삭제한 기억을 사용해 실행하지 않는다.

## 3. 입력부터 결과까지

1. 사용자를 인증하고 버튼 종류·음성/텍스트·사용자 시간대·멱등 키를 받는다.
2. 음성이면 STT로 전사한다. 인식하기 어려운 위치 번호·날짜·시간은 짧게 다시 확인한다.
3. 단순 조회는 도메인 API로 처리한다. 자연어 해석·복합 작업은 DB 큐에 저장하고 `202`와 `run_id`를 반환한다. Adapter는 사용자 runtime이 준비된 뒤 Hermes에 전달하며, 기동 중에는 준비 대기 상태를 제공한다.
4. Hermes가 제안한 도구와 인자를 서버 스키마로 검증한다. 사용자 ID와 권한은 인증 문맥에서 주입한다.
5. 명확하고 허용된 작업은 실행한다. 필수 정보가 부족하면 `awaiting_input` 상태와 질문을 반환한다.
6. DB/외부 도구의 실제 성공을 기준으로 결과를 저장하고 대시보드·알림 작업을 발행한다.
7. 프론트에는 결과 카드와 작업 ID를 보낸다. 자연어 응답만으로 저장 성공을 판단하지 않는다.

전사 모델은 한국어 발화와 호스트 자원을 측정해 고른다. 로컬 STT를 우선 검토하며, 원음 보관은 전사 후 삭제를 기본 제안으로 둔다. 디버깅용 원음 보관은 별도 설정과 기간을 정한다. 텍스트만으로도 같은 기능을 사용할 수 있게 한다.

## 4. Hermes 통합

Hermes의 공식 API를 내부에서 호출하는 Adapter를 둔다. 버전/이미지 digest를 고정하고, 사용할 실행·스트리밍·중단·세션 API를 해당 버전으로 검증한다. 프론트가 Hermes의 내부 응답 형식에 직접 의존하지 않도록 Mori 계약으로 변환한다. [Hermes API 문서](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server).

P1 공용 Gateway가 Knative Serving으로 전환되면 Adapter는 기존 Deployment Service가 아닌 클러스터 내부 Knative Route를 호출한다. 그 HTTP 요청이 공용 Pod를 0개에서 깨운다. Mori API·DB·예약 Worker는 상시 운영하며, 예약·장기 비동기 작업의 상태는 Knative 트래픽 지표가 아니라 Mori DB에서 관리한다. [공용 Hermes 설치·전환 절차](../architecture/knative-serving.md).

초기 Mori 도구 후보:

| 도구 | 역할 |
| --- | --- |
| `parking.save`, `parking.latest` | 주차 기록 저장·최신 유효 기록 조회 |
| `calendar.create`, `calendar.update`, `calendar.list` | 일정 등록·수정·조회 |
| `memory.save`, `memory.search` | 사용자 기록·선호 저장 및 검색 |
| `automation.create`, `automation.update`, `automation.pause` | Mori 예약 규칙 관리 |
| `dashboard.pin`, `dashboard.hide` | 사용자가 원하는 카드 고정·숨김 |
| `research.search`, `research.fetch` | 여행 등에 필요한 외부 정보 검색·읽기 |
| `file.inspect`, `file.transform` | 인증된 업로드의 구조 확인·검증된 변환 요청 |
| `artifact.create` | 구조화된 결과에서 Excel/PDF 생성 |

실제 도구 이름은 구현 시 확정한다. 도구는 전체 DB나 무제한 외부 자격 증명을 에이전트에 전달하지 않고 작업에 필요한 기능만 제공한다. OAuth 토큰은 서버 측 연동 계층에서 사용하고 프롬프트에 넣지 않는다.

무료 사용자의 실행 환경에도 개인별 Hermes home과 상태가 필요하다. 유료 전환 때 프론트 계약과 사용자 ID는 그대로 유지하고 내부 라우팅만 바꾼다. 모델 서버가 바뀌어도 도구 계약을 재사용한다.

### 실행 환경의 수명주기와 업무 작업

[아키텍처의 유휴 중지·재기동 설계](../architecture/plan.md#유휴-중지와-콜드-스타트)를 기준으로 한다. `AgentRun`은 사용자에게 맡은 일, `AgentRuntime`은 그 일을 실행할 환경이다. Pod가 없어도 run과 사용자 데이터는 존재한다.

- runtime 상태는 `sleeping`, `starting`, `ready`, `busy`, `draining`, `failed`다. `sleeping`은 오류가 아니며, 무료 풀에서는 슬롯 할당 상태를 같은 앱용 대기 계약으로 변환한다.
- API는 작업·outbox를 먼저 저장한다. 유료 사용자별 Pod에서는 Dispatcher가 사용자 단위 DB lease/잠금으로 깨우기를 합치고 Runtime Controller가 실제 Pod 수와 준비 상태를 맞춘다. P1 공용 Gateway에서는 내부 Knative Route로 실제 Hermes HTTP 요청을 보내 KPA가 깨우며, 비동기 작업의 완료까지 Pod가 살아 있어야 하는 경로는 별도 검증한다. 앱이 Kubernetes나 `/wake` 엔드포인트를 직접 호출하지 않는다.
- 작업은 준비 전 `queued`다. `wait_reason`은 `agent_starting` 또는 `capacity` 등을 사용하고, 실제 업무 실행 때 `running`으로 전환한다. 준비 ETA는 관측값이 있을 때만 제공한다.
- runtime의 `generation`, 작업의 실행 lease·시도 번호를 검증한다. 만료된 실행자의 도구 쓰기를 거부하고 외부 실행 결과가 불명확하면 조회·대조한 뒤 재시도한다. generation 검증만으로 파일 쓰기를 막을 수 없으므로 home의 단일 작성자 조건도 별도로 지킨다.
- 중지 판단과 작업 배정은 원자적으로 조정한다. `draining`에는 새 작업을 배정하지 않으며, 처리·저장 중인 작업은 단순한 유휴 타이머로 종료하지 않는다.
- `awaiting_input`/`awaiting_approval`의 continuation, 세션 참조, 도구 결과·버전·권한을 DB에 저장한 뒤 안전한 해제 여부를 확인한다. 후속 응답은 같은 run에 연결하고 필요하면 runtime을 다시 준비한다. Hermes의 재개 지원을 실제 버전으로 검증하기 전에는 이 경로를 완료 처리하지 않는다.
- 중복 wake, 작업 취소, 준비 기한 초과, 앱 연결 종료와 별개로 DB의 작업을 정리한다. 사용자가 앱을 닫아도 이미 접수된 일을 자동 취소하지 않는다.
- Controller 재시작·요금제 전환·해지 시 pending wake와 현재 generation을 함께 조정하고 실제 실행자를 대조한다. 새 요청의 권한은 접수·dispatch·도구 실행 시 확인한다.

## 5. 반복 패턴과 자동 스킬 생성

```text
성공한 작업과 사용자의 수정 기록
  → 반복되는 의도·시간·절차 탐지
  → 사용자별 스킬 후보 자동 생성·저장
  → 도구 허용 목록·입력/출력·예시 재생 검증
  → 이미 허용한 범위의 스킬 활성화
  → 실행 결과 관찰·개선·문제 시 이전 버전 복구
```

처음에는 주차·일정 등 지원하는 도메인의 절차 조합부터 학습한다. 반복 횟수나 신뢰도 기준은 예시 데이터를 보고 정하며 ‘3번 쓰면 반드시 학습’ 같은 규칙을 확정하지 않는다.

스킬 내용과 버전을 Hermes가 읽을 수 있는 형식으로 저장하고, Mori에는 소유자·권한·상태·변경 이력·버전 참조를 기록한다. 후보 생성, 검증, 활성 버전을 구분해 실패한 새 버전이 기존 동작을 덮어쓰지 않게 한다. 실행 이력은 어떤 버전을 사용했는지 추적할 수 있어야 한다.

자동화가 스스로 활성화되는 조건은 명시적으로 설정한 동작이거나 사용자가 켠 자동 개인화 범위 안이어야 한다. 기존 주차 기록 조회와 카드 표시는 낮은 영향도의 초기 후보로 두고, 외부 전송·권한 확장·비용 지출은 범위 밖으로 둔다. 기본값은 전체 계획의 검토 항목이다.

웹 페이지와 생성된 스킬 안의 문장은 데이터로 취급한다. 권한 결정은 서버가 수행한다. 자동 생성 코드 실행이 필요하면 별도 sandbox·네트워크·시간·파일 한도를 적용하며, 초기에는 임의 코드보다 검증된 도구 조합을 우선한다.

## 6. 캘린더·예약 실행

시간 값은 실제 실행을 위한 UTC 시각과 사용자가 의도한 시간대·반복 규칙을 함께 저장한다. 종일 일정은 날짜로 표현하고 일반 시각 일정과 구분한다. “내일”, “이번 주 토요일”은 요청 당시 기준 시각과 사용자 시간대로 해석한다.

일정과 알림은 별도 데이터다. 일정 수정·취소 시 이전 알림을 무효화하고 새 알림을 계산한다. 사용자가 지정하지 않은 시간·반복·종료 조건을 모델이 임의로 확정하지 않게 한다.

예약 실행은 DB에서 기한이 된 작업을 원자적으로 가져오고, 실행 lease와 회차별 고유 키를 사용한다. 장애 후 재시도할 수 있도록 상태를 저장하며, 전달 방식은 ‘한 번 이상 시도 가능 + 업무 효과의 중복 방지’로 설계한다. 외부 시스템까지 무조건 정확히 한 번 실행된다고 약속하지 않는다.

DB 갱신과 후속 작업 발행 사이의 유실을 막기 위해 같은 트랜잭션에 outbox 이벤트를 저장하는 방식을 후보로 둔다. 큐 서버가 없어도 Worker가 outbox를 처리할 수 있다.

| 종류 | 지연 실행 정책 초안 |
| --- | --- |
| 주차 표시 | 아직 표시 시간대라면 최신 데이터로 갱신, 지난 시간대이면 건너뜀 |
| 일정 알림 | 의미 있는 허용 지연 이내에서만 발송, 지난 약속 알림을 몰아서 보내지 않음 |
| 조사·문서 작업 | 재개 가능 여부를 확인해 재시도하고 사용자에게 지연 상태 표시 |

초기 캘린더는 서비스 내부 저장이다. 외부 연동을 추가할 때 OAuth 권한·토큰 갱신·외부 event ID·증분 동기화·삭제 반영·충돌 정책을 별도로 구현한다. 전송 결과가 불명확한 경우 외부 ID/중복 방지 키로 조회한 뒤 재시도한다.

AI 예약은 `prewarm_at`에 실행 환경만 준비하고 `scheduled_at` 이후 업무를 시작한다. 주차 표시·기존 일정 알림은 Hermes를 깨우지 않는다. 사전 준비와 직접 요청은 사용자별 한 번의 기동으로 합치고 예약 작업은 회차 키로 중복을 막는다. 예약 변경·취소 시 이전 prewarm과 유지 사유를 무효화한다. `delivery_deadline`은 검색 시작 시각과 구분하며 허용 지연 초과 시 결과 지연·건너뛰기·실패 정책을 표시한다.

## 8. 프론트에 제공할 API 초안

모든 요청은 서버 인증 문맥으로 사용자를 결정한다. 경로의 UUID를 안다는 것만으로 다른 사용자의 데이터에 접근할 수 없어야 한다. 변경 요청에는 멱등 키와 필요 시 버전 조건을 사용한다.

현재 `master`에 있는 공개 경로는 `/health/live`, `/health/ready`, `/v1/auth/providers`, `/v1/auth/{provider}/login`, `/v1/auth/{provider}/callback`, `/v1/auth/exchange`, `/v1/auth/refresh`, `/v1/auth/logout`, `/v1/me`, 주차 저장·최신 조회, 최고 관리자용 `/v1/admin/users` 목록·Pro 승인/회수·권한 이력이다. 아래 나머지는 구현 순서를 논의하기 위한 초안이다. `GET /v1/me`는 구현됐지만 `PATCH /v1/me/preferences`는 아직 없다.

| API | 용도 |
| --- | --- |
| `GET /v1/me`, `PATCH /v1/me/preferences` | 내 정보와 설정 |
| `GET /v1/entitlements` | 기본 기능·등록 한도·현재 개수·정책 버전·초과 상태 |
| `GET/POST /v1/assistants`, `PATCH/DELETE /v1/assistants/{id}` | 논리적 비서 등록·관리. 삭제/보관·집계 효과는 계약에 명시 |
| `GET/POST /v1/widgets`, `PATCH/DELETE /v1/widgets/{id}` | 위젯 표시 구성 등록·관리. OS 위젯 설치와 구분 |

| `POST /v1/actions` | 버튼 또는 자유 텍스트 입력을 업무 작업으로 시작 |
| `GET /v1/runs/{id}` | 저장된 작업 상태·wait_reason·준비 안내·결과 조회. 조회만으로 깨우지 않음 |
| `GET /v1/runs/{id}/events` | SSE 등으로 진행 이벤트 수신; 조회 API로 복구 가능 |
| `POST /v1/runs/{id}/input`, `POST /v1/runs/{id}/cancel` | 추가 답변과 취소 요청 |

| `GET/POST /v1/calendar/events` | 기간별 일정 조회·직접 등록 |
| `PATCH/DELETE /v1/calendar/events/{id}` | 일정 수정·취소 |
| `GET/POST /v1/automations`, `PATCH /v1/automations/{id}` | 반복 작업 조회·생성·수정/중지 |
| `GET /v1/skills`, `PATCH /v1/skills/{id}` | 학습한 절차 조회·활성/중지 |

| `POST /v1/file-transforms` | upload_id와 assistant_id·변환 요청으로 run 시작 |

API 목록은 대표 흐름이며 인증·기기 등록·전체 기록 조회·계정 삭제 등은 계약 구체화 단계에 포함한다. 여행·전사·일반 대화도 오래 걸리는 처리에는 공통 `run_id`를 사용한다.

공통 작업 상태는 `queued`, `running`, `awaiting_input`, `awaiting_approval`, `succeeded`, `failed`, `cancelled`를 초안으로 둔다. 취소 요청 접수와 실제 취소 완료를 구분한다. 오류에는 기계용 코드, 짧은 사용자 문구, 재시도 가능 여부, 추적 ID를 제공한다.

승인 요청은 앱 안에서 확인하고 알림으로도 진입할 수 있다. 모바일 푸시에는 요청을 찾을 식별자를 담고 실제 결정은 같은 인증된 서버 API로 처리한다. 승인한 작업 내용·인자·버전을 고정하며, 내용이 바뀌면 이전 승인을 재사용하지 않는다. 만료·취소·권한 회수와 여러 기기에서의 동시 응답을 확인한 뒤 하나의 결정만 원자적으로 반영한다. 승인 대기 중인 에이전트 작업은 지속 상태로 저장해 연결이나 Pod 재시작 뒤에도 이어간다. 승인 기능을 추가하더라도 이미 허용된 일상 동작마다 새 승인 요청을 만들지는 않는다.

카드에는 `id`, `type`, `title`, `data`, `actions`, `recorded_at`, `visible_from`, `visible_until`, `updated_at` 등을 둔다. 카드 종류별 `data` 스키마와 허용된 `actions` 목록을 정의해 프론트가 임의 HTML이나 모델 문자열을 실행하지 않게 한다.

구현에 앞서 OpenAPI 계약·예시 응답·오류 사례를 `master`의 코드와 함께 관리하고, 주요 결정과 변경 이유는 `plan`에 남긴다.

### 비서·위젯 등록 한도

무료도 검색·파일·개인 스킬 등 기본 기능을 사용하며, 비서와 위젯 등록은 각각 약 3개를 잠정 방향으로 둔다. 유료의 등록 개수에는 정해진 상한을 두지 않되 호출량·파일 용량·동시 작업·활성 Pod 수는 별도 정책이다. 등록 시 Pod를 즉시 생성하지 않는다.

`Assistant`, `WidgetConfig`, 실제 기기 설치 수를 구분한다. 기본 비서 포함 여부, 보관/중지 항목의 집계, 같은 위젯의 여러 기기 설치를 한 개로 볼지는 P0에서 확정하고 정책 버전으로 관리한다. 특히 자동 대시보드 카드 갱신이나 기존 위젯 내용 변경을 매번 새 위젯 등록으로 세지 않는다.

비서·위젯의 생성과 개수 증가는 서버 트랜잭션/잠금으로 처리한다. 동시에 두 번 생성하거나 자동 학습과 수동 등록이 겹쳐도 한도를 넘지 않아야 한다. 초과 시 `REGISTRATION_LIMIT_REACHED`와 대상 종류·현재 개수·한도·가능한 행동을 반환한다. 자동 학습은 기존 기록을 덮어쓰지 않고 미활성 제안으로 남긴다.

유료→무료 전환 시 기존 대화·스킬·파일·일정을 자동 삭제하지 않는다. 초과 항목의 신규 실행 허용·유예 기간·사용자가 선택할 항목은 결정 전이며, API와 화면에 동일하게 반영한다. 요금제 개수 제한과 자동화 실행 권한을 혼동하지 않는다.

## 9. 정기 검색·여행·파일 처리

### 자체 호스팅 검색과 개인 이력 — 2026-09-21 설계

외부 유료 검색 API를 필수로 두지 않고 SearXNG를 공유 내부 서비스로 운영하는 안부터 검증한다. Hermes는 기본 SearXNG provider를 사용하고 본문 추출은 별도 도구로 다룬다. 아직 관련 Pod·설정·도구 이력 저장 기능을 배포/구현하지 않았다. [검색·경량화 설계](../architecture/hermes-search-runtime.md).

공유 검색 서비스를 호출하더라도 `user_id`·`conversation_id`·`run_id`는 서버 인증 문맥에 묶고 검색어·실행 시각·출처·오류를 사용자별 이력에 연결한다. SearXNG 자체 로그를 개인 기억 저장소로 삼지 않는다. 원문 보관·캐시·삭제 정책은 출처 조건과 사용자 소유권에 맞춘다. 검색 결과를 받은 뒤 후속 모델 호출이 이루어졌는지 도구 이벤트로 확인하며, 모델의 “검색했다/저장했다”는 문장만으로 성공 처리하지 않는다.

### 정기 정보 브리핑

코스피 등 정기 브리핑은 실행 시점의 검색/데이터 제공 도구로 자료를 확보한다. 값의 기준 시각과 검색한 시각, 출처 URL, 지연 여부를 저장하고 알림·PDF가 같은 결과를 참조하게 한다. 요일·휴장일·전달 방식·허용 지연이 모호하면 등록 전에 확인한다. 검색 실패·자료 지연은 성공처럼 표시하지 않고 마지막 결과의 시각과 재시도 방법을 제공한다. 이 작업에는 투자 판단·거래 실행을 포함하지 않는다.

### 여행과 결과 생성

1. 여행 조건을 구조화하고 빠진 필수 조건을 짧게 확인한다.
2. 검색 도구로 자료를 읽고 출처 URL·확인 시각을 함께 저장한다.
3. 일자별 활동·이동·예상 비용·참고 링크의 구조화된 여행 계획을 만든다.
4. 같은 계획 데이터에서 앱 결과, Excel과 PDF를 생성해 서로 다른 내용을 만들지 않게 한다.
5. 파일 생성 결과를 열어 한국어 폰트·표·페이지 잘림·링크·파일 손상을 검증한다.
6. 작업 소유자에게만 결과를 제공하고 다운로드 만료·삭제를 처리한다.

운영시간·가격·교통 정보는 확인 시점을 밝히고, 확인하지 못한 값은 추정 또는 미확인으로 구분한다. 결과물은 검색한 웹페이지의 실행 지시를 따르지 않는다. 원격 URL 조회에는 내부 주소 접근 방지, 리다이렉트 검증, 응답 크기·시간 제한을 둔다.

Excel은 검증된 템플릿과 라이브러리로 만들고 외부 텍스트의 수식 실행을 막는다. PDF는 정해진 레이아웃·폰트로 렌더링한다. 에이전트가 생성한 코드를 서버 권한으로 바로 실행하는 방식을 기본으로 삼지 않는다.

### Excel 업로드·정리·결과 전달

1. 인증된 사용자의 업로드 의도를 만들고 크기·형식·보관 기한을 안내한다. 업로드 완료 요청만 신뢰하지 않고 저장소의 실제 수신·크기·해시·형식을 검증한다. 업로드 URL은 짧은 유효 기간과 소유자/파일 범위를 갖는다.
2. 원본은 변경하지 않고 보존한다. 초기 지원은 `.xlsx`를 우선 후보로 두며 `.xls`·`.xlsm`·암호화 파일·매크로·외부 연결은 지원 여부를 별도 결정한다. 압축 해제 크기·시트/행 수·처리 시간 제한을 둔다.
3. 제한된 Worker가 시트 이름·열·자료형·일부 미리보기를 추출한다. 날짜 열·기간·집계 방식·수식/서식 보존 범위가 모호하면 `awaiting_input`으로 필요한 것만 확인한다. 파일 전체를 무조건 프롬프트에 넣지 않는다.
4. 확정한 변환 명세를 버전으로 저장하고 허용된 정렬·필터·그룹 집계부터 처리한다. 원본 수식을 임의 실행하거나 매크로·외부 링크를 열지 않는다. 수식 캐시가 오래됐거나 보존이 불가능한 부분은 결과에 밝힌다.
5. 원본/결과 연결, 변경 요약, 미리보기, 새 `.xlsx` Artifact를 만든다. 결과를 다시 열어 행 수·집계 합계·자료형·한글·시트·손상 여부를 확인한다. 작업에서 보존하기로 한 수식/서식도 검증한다. 검증 실패 시 원본을 유지하고 실패 이유와 재시도 수단을 제공한다.
6. 앱이 종료돼도 같은 `run_id`로 결과를 찾는다. 다운로드마다 소유권·만료를 확인하고, 원본/결과/임시 파일/도구 캐시 삭제를 보관 정책에 연결한다. 처리 중 삭제 요청은 후속 쓰기·생성을 중단하거나 격리한 뒤 완료 상태를 확정한다.

파일 처리 Worker의 lease는 Hermes runtime과 분리한다. Hermes가 후속 결과를 기다리는 동안 안전한 continuation을 저장했다면 runtime을 해제할 수 있지만, Worker를 함께 죽이거나 결과를 잃어서는 안 된다. 최초 구현은 이 분리 재개가 검증되지 않은 작업을 끝까지 활성 상태로 유지한다.

## 10. 핵심 검증 기준

| 영역 | 반드시 확인할 시나리오 |
| --- | --- |
| 한국어 입력 | “지하 삼 층 비 십이”, 위치 정정, 상대 날짜, 오전/오후, 불명확한 시간 |
| 기록 일관성 | 새 주차 기록 이후 이전 위치가 최신으로 나오지 않음, 삭제한 기억의 재등장 방지 |
| 일정 | 재전송 중복 방지, 수정 시 알림 교체, 취소 후 알림 차단, 시간대 처리 |
| 예약 복구 | Worker 중단·lease 만료·재시작, 같은 회차 동시 실행, 외부 성공 후 응답 유실 |
| 사용자 격리 | 다른 계정의 ID/프로필/파일/스킬/다운로드 링크 접근 차단 |
| 스킬 | 생성·저장·재사용 증거, 잘못된 후보 비활성, 활성 버전 복구, 권한 밖 실행 차단 |
| 모델 | 잘못된 JSON·도구 이름·무한 반복·타임아웃·GPU 장애에서 실패 상태 복구 |
| 결과물 | 실제 `.xlsx`/`.pdf` 열기, 한국어 렌더링, 출처·확인 시점, 접근 만료 |
| 유료 환경 | 동시 wake·유휴 중지 경합·시작 실패·강제 종료·등급 전환에도 runtime과 home 작성자 하나 유지 |
| 예약 사전 준비 | Pod 0개에서 정기 검색 준비, 예약 변경/취소 반영, 늦은 준비·전원 복구의 중복 방지 |
| 등록 한도 | 동시 생성·자동 생성·등급 변경의 개수 일관성, 기존 데이터 보존, 기기 설치 집계 |
| Excel 입력·정리 | 잘못된 형식·큰 압축·모호한 열·수식/서식·업로드 중단·원본 보존·결과 검증·삭제 경합 |
| 앱 복구 | 준비 대기 중 앱 종료·재접속, 같은 run 복구, 중복 전송·취소·후속 승인과 기동 경합 |

전체 흐름 인수 예시는 “주차를 음성으로 저장 → 재접속 후 조회 → 평일 아침 표시 등록 → 같은 작업의 재시도 → 중복 없이 표시 → 스킬 자동 저장·재사용 확인”이다. 두 계정으로 같은 흐름을 실행해 데이터가 섞이지 않는 것까지 확인한다.
