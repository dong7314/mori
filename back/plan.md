## 1. 현재 구현과 후속 설계의 경계

현재 `master` `53b0fa6`, API 0.7.0/`0007_parking_display`다. 저장소는 PostgreSQL이다. 기존 소셜 인증·관리자 Pro·주차·채팅/SSE에 메모·일정·알림 목표·텍스트 문서·기능 정의/버전/결과·대시보드·보관함·계정/테마/요금제 조회를 추가했다. 주차 용도·상시/시간 표시와 텍스트 문서 10MB를 반영했고 204개 테스트, Ruff, OpenAPI 스냅샷 검사가 통과했다. [기존 구현 계약](screen-api-implementation-2026-09-30.md)과 [0.7.0 변경](parking-document-update-2026-10-02.md)을 정확한 경로·필드·오류의 기준으로 사용한다.

아래의 장기 데이터 모델과 예약 흐름은 목표 설계다. 현재 사용자 기능은 버전이 있는 work 정의와 텍스트 결과를 저장하며 Hermes 스킬 파일 동기화·cron·prewarm·기기 푸시·결제·실시간 시세 공급자는 미구현이다. 실제 GPU 모델의 새 JSON 계약과 k3s 왕복 검증도 남아 있다.

React 웹 + React Native/WebView 방향에 맞춰 [모바일 클라이언트 계약](mobile-client-contracts.md)을 추가했다. 기존 소셜 인증·도메인 API는 재사용하고 제품용 웹 세션, WebView 일회용 세션 교환, client-config, 기기 등록·위젯 snapshot을 단계적으로 만든다. 이 신규 계약은 아직 OpenAPI 0.7.0에 없다.

실제 테이블은 도메인·트랜잭션 경계를 검토해 정한다. 모든 논리 모델을 즉시 별도 테이블로 만들 필요는 없다. 기존 `parking_records`, `conversations`, `chat_turns`를 버리거나 모델 이름만 바꿔 완료 처리하지 않는다.

### 선택적 입력과 실행 가능성

사용자에게 title/description/시간/contents/work 전부를 요구하지 않는다. 제목은 의도에서 생성하고, 설명/내용/시간은 없을 수 있다. 서버 ID·소유자·버전·유형은 서버가 채운다. 순수 텍스트 결과는 work 없이 저장 가능하다. 실행형 기능은 수행 내용/입력이 확인돼야 하고, 예약형은 유효한 시간대·단발/반복 규칙도 필요하다. 부족하면 초안으로 저장하거나 질문하며 활성 예약 성공으로 답하지 않는다.

UI template과 work는 분리한다. 필드에 임의 실행 코드를 담지 않으며 서버가 허용 도구·출력 스키마를 검증한다. 저장되는 텍스트/외부 자료는 사용자 지시와 구분한다.

## 5. 기능을 먼저 확인하는 채팅

1. 현재 사용자/대화 소유권과 서버 runtime 바인딩을 확인한다.
2. Hermes가 현재 사용자의 활성 기능 목록/설정과 필요한 스킬 버전을 Mori에서 조회한다. 기본 기능과 사용자 커스텀을 함께 검색하되 다른 사용자의 기능을 섞지 않는다.
3. 의도에 적합한 기능을 고른다. 후보가 여러 개여서 동작이 달라지면 필요한 조건만 질문한다. 비슷한 이름만으로 임의 예약을 실행하지 않는다.
4. 기능이 있으면 선택한 버전과 입력을 고정하고 허용 도구를 실행한다. 결과는 Mori가 스키마/소유권/버전을 검증해 저장한다.
5. 기능이 없으면 일반 대화/일회성 작업으로 진행한다. 요청에 따라 검색할 수 있지만 매번 기능 생성·카드 게시를 강제하지 않는다.
6. 저장된 결과/표시 규칙에 따라 대시보드를 갱신하고, 대화에는 결과 참조와 실제 진행 상태를 남긴다.

현재 JSON 작업 제안은 주차 외에 메모·일정·알림 목표·기능 생성과 feature_run 선택으로 확장했다. 서버가 활성 기능과 버전을 확인해 재호출하고 텍스트 결과를 저장한다. 새 계약의 실제 Hermes 준수 여부는 별도 검증해야 한다. 프론트가 feature ID를 명시하면 대상 접근권한을 검증하며, 본문으로 user_id/runtime URL을 덮어쓰게 하지 않는다.

Hermes 내장 스킬 파일만 존재하고 Mori에는 이름만 있는 상태를 제품 등록 완료로 보지 않는다. Mori의 버전 조회 도구/API와 Hermes 로컬 실행 사본의 동기화가 필요하다. 삭제/중지/권한 회수된 버전을 오래된 캐시로 새로 실행하지 않도록 dispatch 직전 확인한다.

### 도구/API 내부 계약 초안

`features.list`, `features.get`, `skills.get_version`, `features.save_draft`, `features.activate`,
`feature_results.publish`, 도메인별 주차/메모/일정/알림 작업 도구를 후보로 둔다.
프롬프트 지시뿐 아니라 서버가 사용자·실행 ID·허용 범위를 주입/검증한다. 구체 도구 이름은 구현 시 고정한다.

## 6. 커스텀 기능 생성·변경

```text
자연어 요청 → 기존 기능/생성 의도 확인 → 구조화 초안
 → 공통 템플릿·입력/결과·work·선택적 시간 검증
 → 아이콘 후보/기본 자산 → Mori 정의·스킬 버전 저장
 → 실행 가능 상태 활성화 / 예약 동기화
 → Hermes가 같은 버전을 조회·재사용
```

초안·검증·활성·중지·보관 상태를 구분한다. 제목/설명만 수정하는 것과 실제 work/권한/예약 변경을 구분해 새 버전과 동기화를 적용한다. 이미 진행 중인 실행은 시작 시 버전을 참조하고, 이후 실행부터 새 버전을 사용한다. 변경/중지·삭제 시 실행/예약/표시/이전 결과 보존의 효과를 명시한다.

생성/수정은 요청 키와 revision으로 중복·덮어쓰기를 방지한다. 예약 동기화 실패는 준비 중/실패로 남기며 이전 활성 버전을 불명확하게 덮어쓰지 않는다. 새 기능을 저장하는 것과 바로 한 번 실행하는 것은 별도 의도다.

아이콘은 Hermes가 검색 후보를 제안할 수 있다. 후보 URL만을 영구 UI 계약으로 쓰지 않고 서버에서 URL/응답 형식/크기·출처를 확인해 자산 참조로 저장하거나 기본 아이콘으로 대체한다. 외부 수집은 내부 주소 접근·실행 가능한 이미지 내용 등을 제한하고 오류를 분리한다. 사용 조건·보관 기간·교체 정책은 후속 확정이다.

## 7. 대시보드와 결과 projection

대시보드는 **현재 시간에 맞는 저장 데이터의 조회 모델**이다. 요청마다 Hermes가 레이아웃을 생성하거나 검색을 다시 수행하지 않는다.

- 시간 카드: 활성 DisplayRule의 구간과 현재 사용자 시간대에 해당하는 주차/뉴스/주가/일정/커스텀 결과.
- 시간 없는 목록: 메모·문서·무시간 기능 결과. 결과 타입·저장/갱신 시각과 안정적인 정렬·페이지 처리를 제공한다.
- 중복되는 카드/결과는 feature/result/run 식별자로 연결한다. 한 예약 회차의 재시도가 새 카드 여러 개를 만들지 않는다.
- 실행/표시/알림 시각을 구분하고 최신 결과가 없으면 예정/실행 중/실패 상태를 반환한다.
- 이전 결과를 보여줄 때 stale·기준 시각·마지막 성공을 표시한다. 출처/가격 시점이 없는 데이터를 최신으로 포장하지 않는다.
- 클라이언트에 server_time, next_refresh_at, 표시 구간과 template_version을 제공하는 안을 검토한다.
- 동시에 표시할 항목의 우선순위는 가까운 일정/알림, 사용자 설정 등을 후보로 두되 숫자·정렬 정책은 미정이다.

습관은 명시한 선호를 우선한다. 관측으로 추정한 출근 시각은 근거/갱신 시각을 보관하고 사용자 변경·휴일·시간대 변화에 대응한다. 근거가 없으면 09:00 출근/08:30 표시를 임의로 만들지 않는다.

## 8. 스케줄·예약·알림 계약

### 시간의 네 가지 의미

| 값 | 의미 |
| --- | --- |
| execute_at/recurrence | 자료 수집 등 work를 시작할 때 |
| ready_by | 결과 완료를 원하는 목표 시각(선택) |
| show_from/show_until | 대시보드에 표시할 구간 |
| notify_at | 기기에 알림을 전달할 목표 시각 |

UTC 실행 시각과 IANA 시간대·원래 반복 의도를 함께 관리한다. “30분 뒤”는 요청 접수 기준 목표 시각을 생성하고 재시도 때 새 30분으로 밀지 않는다. “내일”·요일·종일 일정·여행 중 시간대·DST·휴일은 사용자 문맥으로 계산하며 모호하면 확인한다.

개인 약속 캘린더와 자동 기능 예약은 관련되지만 같은 목록에 무조건 섞지 않는다. 직접 폼과 AI 등록은 같은 도메인 서비스·버전/멱등 계약을 쓴다. 수정/취소 때 이전 알림과 표시 규칙도 동기화한다.

### 실행 환경의 수명주기와 업무 작업

합의한 방향은 Hermes가 AI 예약 작업 내용/cron을 영속 home에 보관해 실행하고, Mori는 job ID·스킬 버전·다음 실행·prewarm 등 기동 메타데이터를 관리하는 것이다. 기능 정의의 기준은 Mori이며 Hermes cron은 해당 활성 버전/입력 참조를 실행한다. 양쪽이 동일 예약을 각각 수행하지 않는다.

Mori의 항상 실행되는 worker가 사전 기동·동기화 재시도·실행 lease·완료 callback을 관리한다. health 요청 한 번으로 예약 실행이 끝날 때까지 Pod가 살아 있다고 가정하지 않는다. 실제 Knative 유지 방식, cron 프로세스 구동, API/앱 연결 종료와 독립적인 완료 보장은 후속 검증 대상이다.

Mori DB 변경과 Hermes 예약 갱신은 분산 작업이다. outbox·revision·회차 고유 키·동기화 상태를 두고 실패/재시작 시 조회·대조한다. 외부 효과까지 무조건 정확히 한 번 실행된다고 약속하지 않는다. 삭제/중지 시 이전 prewarm·활성 실행·표시/알림 처리 정책이 필요하다.

단순 카운트다운·기존 기록 표시·저장된 일정 알림은 결정된 데이터/시간으로 처리하므로 Hermes를 계속 켜 두지 않는다. 뉴스/커스텀 AI 예약은 실행 시 agent가 필요하다. 클라이언트의 카운트다운은 표시일 뿐 알림 예약/전달 성공 상태를 바꾸지 않는다.

## 9. 현행 API 계약과 후속 확장

현행 입력·응답·권한·페이지 처리는 [기존 화면 API 기록](screen-api-implementation-2026-09-30.md), [API 0.7.0 변경](parking-document-update-2026-10-02.md)과 master의 OpenAPI를 따른다. 이전의 PATCH features, /activate, /pause, /runs 경로 제안은 현행 계약이 아니다.

| 계약 | 현재 지원 |
| --- | --- |
| `/v1/conversations`와 메시지/실행 | 검색·생성·이름/고정 PATCH·삭제·채팅 SSE·결과 참조 |
| `/v1/feature-catalog`, `/v1/features` | 기본 정의, 내 기능 GET/POST/GET 상세/PUT, POST /{id}/state |
| 기능 버전·결과 | GET /{id}/versions/{version}, /{id}/results, /v1/feature-results/{id} |
| `/v1/dashboard?hours=24`, `/v1/library` | 시간 카드/예정 그룹과 기록 목록 조회; hours는 0·3·5·24 중 하나를 보냄 |
| `/v1/notes`, `/v1/calendar/events`, `/v1/reminders` | 생성·조회·PUT·삭제·복원; 알림은 /{id}/cancel |
| `/v1/documents` | 텍스트 원문 생성·조회·다운로드·삭제·복원 |
| `/v1/me`, `/v1/me/settings` | 프로필 조회·이름 PATCH, 테마 GET/PUT |
| `/v1/plans`, `/v1/me/subscription` | 무료·Pro 안내/권한과 결제 상태 조회 |
| `/docs`, `/scalar`, `/openapi.json` | Swagger·Scalar·동일 OpenAPI 명세 |

실행 요청은 채팅 하나를 사용한다. 기능 화면에서 실행할 때도 메시지 body의 feature_id로 선택하며 별도 검색 API를 만들지 않는다. feature.selected와 result.saved SSE는 실제 선택/저장 이후 전송한다. 내부 추론은 공개하지 않는다.

예약 동기화·기기 등록/전달·결제/해지 API, Hermes가 Mori 스킬 저장소를 직접 조회하는 전용 도구는 후속이다. 마이의 /preferences 및 /summary는 제거했다.

모바일 후속 B-18은 제품 웹 세션과 client-config, B-19는 기기 등록·회수/알림·위젯을 담당한다. [후속 경로·필드와 검증 기준](mobile-client-contracts.md)은 설계 초안이며 구현 시 Swagger/Scalar·생성 클라이언트를 같이 갱신한다. 앱 build나 브리지 capability를 사용자 권한으로 신뢰하지 않는다.

## 10. 라이선스·권한·격리

현재 Free/Pro는 관리자 승인 방식이며 개인 Pod 자동 생성과 결제는 없다. 마이의 결제 기능은 신규 목표다. 가격/주기/취소·환불·결제 제공자·기존 승인 Pro의 전환 규칙이 결정된 뒤 구현한다. 클라이언트 구매 표시만으로 권한을 변경하지 않고 서버가 검증된 결제 상태와 연결한다.

과거 무료 비서/위젯 약 3개 제안은 기능/스킬/예약/실행량의 한도로 자동 적용하지 않는다. 어떤 단위를 집계할지 새 기획으로 결정한다. 등급이 바뀌어도 기존 기록을 자동 삭제하지 않으며 초과 기능/예약의 유지 정책은 별도 정의한다.

기능/스킬/결과/아이콘·파일/예약에 사용자 권한을 적용한다. 공유 실행 자원은 데이터 공유를 뜻하지 않는다. 현재 공용 Hermes는 한 명만 허용하며, DB에 user_id를 추가하는 것만으로 agent home의 격리가 완성되지 않는다.

## 11. 다음 구현과 검증 기준

1. API 이미지/0007 마이그레이션을 배포하고 인증된 실제 Hermes 채팅으로 새 작업 제안을 검증한다.
2. 제품 React/RN 기반과 B-18 웹 세션 연계를 만든 뒤, 로그인→주차/대시보드→채팅/SSE를 먼저 연결한다. 이후 일정·메모·문서·기능 화면으로 확장한다.

4. 예약 worker의 prewarm·실행 유지·결과 반영 및 기기 전달을 구현한다.

204개 테스트는 인증·소유권·멱등 생성·revision·삭제 복원·날짜 경계·기능 선택·결과 저장에 더해 주차 표시·이관과 10MB 원문 경계를 검증한다. 모델 HTTP는 mock이므로 GPU 모델의 계약 준수나 예약 유지, 앱 종료 후 푸시가 검증된 것은 아니다.
