# 기능 중심 개인 비서 — 2026-09-29 제품 시나리오

[전체 계획](../plan.md) · [프론트](../front/plan.md) · [백엔드](../back/plan.md) · [아키텍처](../architecture/plan.md)

사용자가 친구와 논의한 9월 29일 제품 기준이다. 이후 확정한 마이 범위는 [9월 30일 계정 정책](account-scope-2026-09-30.md), 화면별 현황은 [화면 기획서](screen-spec/README.md)와 [PoC 기록](../front/poc-validation-2026-09-30.md)을 우선한다. 이 문서의 화면과 데이터 계약은 **목표 설계**이며 구현 완료 보고가 아니다. 이전 계획과 충돌하면 이번 시나리오를 우선한다. 상세 필드명과 기본값은 아래에서 제안으로 구분한다.

## 1. 제품의 중심

Mori가 미리 만든 기본 기능과 사용자가 자연어로 만드는 커스텀 기능을 하나의 비서가 사용한다.
사용자는 기능마다 다른 명령법을 배우지 않는다. 대시보드의 채팅이나 마이크로 요청하면 Hermes가 먼저 사용자의 기능을 확인하고 적합한 기능을 사용한다. 적합한 기능이 없으면 일반 대화/일회성 작업으로 처리한다.

기능의 실행 방법과 결과 화면은 분리한다. 기본 기능은 제품이 만든 전용 화면·상호작용을 사용한다. 커스텀 기능은 제품의 공통 카드/상세 템플릿에 맞는 데이터만 생성하므로 기능마다 임의의 화면이 생기지 않는다.

## 2. 사용자 요구로 확정한 방향

| 영역 | 방향 |
| --- | --- |
| 기본 기능 | 주차 기록 관리, 뉴스 정보 정리, 주식 주가, 메모, 스케줄 관리, 알림 |
| 커스텀 기능 | 자연어로 시간 맞춤형 예약 또는 텍스트/정리 기능 생성·저장·재사용 |
| 탭 | **대시보드 / 스케줄 / 대화 / 기능 / 마이** |
| 대시보드 상단 | 현재 시간대에 필요한 주차·뉴스·주가·일정·시간 지정 커스텀 기능을 캐러셀로 표시 |
| 대시보드 하단 | 시간이 없는 메모·문서 정리 등의 결과를 해당 공통 레이아웃의 목록으로 표시 |
| 대시보드 입력 | 채팅창 선택 시 대화 패널이 올라오고, 마이크는 음성 상호작용 후 같은 대화로 연결 |
| 대화 이어가기 | 텍스트·마이크를 번갈아 사용하고 대화 목록에서 과거 대화를 재개 |
| 스케줄 | 달력/주/일 보기, 직접 입력·수정과 AI 등록을 함께 지원 |
| 기능 탭 | 기본 기능과 내가 만든 기능 확인, 자연어 커스텀 기능 추가 |
| 기본 기능 상세 | 제품이 만든 전용 애니메이션과 조작; 예: 알림 카운트다운 |
| 커스텀 상세 | title, description, 시간, contents, work에 대응하는 통일된 UI |
| 마이 | 계정 정보, 무료/유료 라이선스·결제, 설정 |

대시보드 맨 아래 최근 대화 목록은 사용자가 제시한 선택안이다. 전체 대화 탭과 중복되지 않는 짧은 최근 목록을 후보로 두고 항목 수·기본 노출 여부는 화면 검토로 정한다.

## 3. 용어와 저장 대상

| 개념 | 예시 | 구분 이유 |
| --- | --- | --- |
| 기능 정의 | 기본 주차 기능, 나만의 아침 IT 뉴스 기능 | 이름·아이콘·UI 템플릿·입출력·가능한 동작 |
| 내 기능 설정 | 관심 키워드, 출근 시간대, 종목, 지역 | 같은 기본 기능도 사용자마다 다름 |
| 스킬 버전 | 뉴스를 검색하고 본문을 확인해 요약하는 절차 | 실행 절차의 수정·재사용·복구 |
| 예약 | 평일 09:00 실행, 08:30~09:10 표시 | 실행과 표시 조건을 관리 |
| 실행 | 오늘 09:00 뉴스 수집 1회 | 성공·지연·실패·중복 방지 |
| 결과 | 오늘 뉴스 요약, 최근 주차 위치, 메모 | 실제 데이터·출처·기준 시각 |
| 표시 카드 | 현재 보여줄 뉴스 요약 카드 | 결과를 UI에 맞춰 보여주는 표현 |

기능을 만드는 것과 한 번 실행한 결과를 저장하는 것은 다르다. 메모 하나를 쓸 때마다 새 메모 스킬을 생성하지 않는다. “오늘 날씨 알려줘”라는 일회성 요청을 사용자 의도 없이 매일 예약으로 만들지 않는다.

## 4. 공통 카드와 상세 화면의 계약

사용자가 title/description/work 같은 개발 필드 이름을 외우거나 전부 입력할 필요는 없다. 자연어를 Hermes가 구조화하고, 기능 수행에 필요한 정보가 부족할 때만 짧게 질문한다.

| 사용자 개념 | 설계 제안 | 없을 때 |
| --- | --- | --- |
| title | 기능/결과 제목 | 요청에서 짧은 제목을 만들어 편집 가능하게 제공 |
| description | 목적·요약 | 생략 가능 |
| 시간 | 단발/반복 실행, 표시 시작·종료, 시간대 | 생략 가능; 예약 없는 기능/결과로 저장 |
| contents | 요약, 목록, 표, 메모, 파일 등 허용된 내용 블록 | 선택 사항; 결과가 없으면 빈 블록을 억지로 만들지 않음 |
| work | 어떤 자료로 무슨 일을 하고 어디에 반영할지 | 순수 메모/보기는 생략 가능. 실행 기능이면 의도가 확인돼야 함 |
| 아이콘 | 기본 제공 자산 또는 검색으로 찾은 적합한 이미지 | 공통 기본 아이콘 사용 |

이는 사용자 입력의 선택성이다. 서버 식별자·소유자·템플릿 버전 등 시스템 관리 값은 서버가 필수로 생성한다. “예약 실행”을 활성화하려면 실행할 work와 해석 가능한 시간/시간대가 필요하지만, 기능을 초안으로 저장할 때부터 모든 필드를 강제하지 않는다.

공통 내용 블록 제안: 텍스트·목록·체크리스트·표·수치·링크·이미지·파일 참조. 초기 지원 블록은 구현 단계에서 좁혀 확정한다. 커스텀 기능이 HTML/JavaScript/CSS를 만들어 앱에서 실행하는 방식은 사용하지 않는다. Hermes는 허용된 템플릿과 블록을 선택하고 프론트가 렌더링한다.

기본 기능의 전용 화면도 제목·상태·기준 시각·결과 ID·사용 가능한 동작이라는 공통 외곽 구조를 공유한다. 커스텀 기능 역시 여백·글꼴·색상·전환 애니메이션을 공유하되 임의의 전용 인터랙션은 생성하지 않는다.

## 5. 대표 시나리오

### A. 주차 기록과 출근 시간대 카드

1. “오늘 지하 3층 B16에 주차했어. 내일 출근할 때 알려줘.”
2. Hermes가 내 기능에서 주차 기록 기능을 찾는다.
3. Mori에 사용자 주차 기록을 저장한다.
4. 기존에 저장된 출근 습관/선호가 09:00 출근을 뒷받침하면 08:30부터 표시하는 규칙을 구성한다. 30분 전은 이번 사례의 값이지 모든 사용자 고정 기본값이 아니다.
5. 습관 근거가 없으면 출근 시각을 질문한다. 출근 요일·휴일·시간대는 사용자의 설정과 규칙을 사용한다.
6. 실제 저장된 표시 규칙을 답변에 안내하고 수정·중지할 수 있게 한다.
7. 내일 해당 시간대 대시보드 상단에 최신 주차 위치와 기록 시각을 보여준다. 사용자가 그 전에 다른 위치를 저장했다면 새 위치를 반영한다.

대시보드 표시와 푸시 알림은 별도 효과다. “알려줘”를 카드만으로 처리할지 알림까지 보낼지는 사용자의 알림 선호/문맥으로 결정하고 답변에 실제 등록 결과를 구분해 알린다. 아직 선호가 없다면 필요한 채널만 확인한다.

### B. 오전 9시 뉴스 수집과 요약

1. “매일 오전 9시에 AI 뉴스를 수집해서 정리해줘.”
2. 기본 뉴스 기능을 재사용해 키워드·반복·시간대를 저장한다. “9시”만 말했을 때 매일인지 오늘 한 번인지는 문맥으로 확인한다.
3. Mori는 예약 기동 메타데이터를 동기화하고, AI 실행이 필요하면 사전 기동한다.
4. Hermes가 09:00에 검색/추출/요약을 수행하고 결과를 Mori에 반영한다.
5. 09:00 카드에는 결과 준비 전 “수집 중”, 준비 후 실제 요약·출처·수집 시각이 표시된다.
6. 실패하면 이전 결과를 오늘의 새 결과처럼 표시하지 않고 마지막 갱신 시각과 지연/실패 상태를 표시한다.

“9시에 요약을 받아보고 싶다”는 9시 실행 시작과 다르다. 완료 목표가 지정되면 시작 시각·prewarm을 따로 계산하는 후속 정책이 필요하며 정확한 완료 시간을 보장하지 않는다.

### C. 주가 확인

관심 종목과 원하는 시간/빈도를 등록하면 상단 시간 카드와 주가 전용 상세 화면에 가격·시장·통화·기준 시각·지연 여부·출처를 표시한다. 사용자가 지정한 종목이 모호하면 거래소/종목을 확인한다. 데이터 제공자·지연 허용·호출 주기는 미정이다. 현재 검색 결과를 실시간 시세로 간주하지 않는다. 자동 매매는 이번 기능 범위가 아니다.

### D. 메모와 문서 정리

“이거 메모해줘”는 시간 없는 메모 결과로 저장해 상단 시간 캐러셀 아래 목록에 표시한다. 제목만 있는 메모나 짧은 내용도 자연스럽게 표현한다. 파일을 정리한 경우 요약과 실제 결과 파일을 연결하며, 파일 이름만 존재하는 상태를 문서 처리 완료로 표시하지 않는다.

기본 기능 첫 목록에는 메모가 포함된다. 문서 정리는 중요한 결과 유형이지만 독립 기본 기능으로 처음부터 제공할지와 지원 형식은 후속 범위 결정 사항이다.

### E. 30분 뒤 알림과 카운트다운

1. 대시보드에서 “30분 뒤에 나한테 알림 줘.”
2. 기본 알림 기능을 선택해 요청 접수 시각 기준 목표 시각을 저장한다.
3. 등록 성공 이벤트와 알림 ID를 받고, 사용자가 해당 대화에서 작업 중이면 알림 상세 화면으로 이어진다.
4. 상세 화면에는 제품 전용 카운트다운 애니메이션과 목표 시각·취소/변경 동작을 제공한다.
5. 앱이 백그라운드이거나 다른 작업으로 이동한 경우 강제로 화면을 바꾸지 않고 결과 카드/딥링크로 접근하게 한다.
6. 남은 시간은 서버 목표 시각과 기기 시계 보정을 기준으로 다시 계산한다. 앱이 닫혀도 실제 알림 예약은 유지돼야 한다.

카운트다운 화면, 알림 예약, 실제 기기 전달은 각각 별도 상태다. 화면의 숫자가 0이 되는 것을 알림 전달 성공으로 처리하지 않는다. 이 알림을 매초 Hermes가 계산할 필요는 없다.

### F. 내 커스텀 기능 만들기

“평일 저녁 7시에 오늘 저장한 메모를 모아서 할 일을 정리해줘. 제목은 퇴근 정리로 해줘.”

1. 내 기능에 동일 목적의 기능이 있는지 확인해 새 기능/기존 수정 의도를 구분한다.
2. Hermes가 제목·시간·work·필요한 입력과 공통 UI 템플릿을 구성한다. description/contents는 선택 사항이다.
3. 적합한 로고/아이콘을 검색할 수 있다. 검색 후보를 검증해 자산 참조로 저장하고 실패하면 기본 아이콘을 사용한다. 아이콘 때문에 기능 생성 전체가 실패하지 않는다.
4. Mori에 기능 정의·스킬 버전·사용자 설정을 저장한다. 실제 구현에서는 정의와 실행 가능한 스킬을 같은 버전으로 연결한다.
5. 시간 규칙이 있으면 Hermes 예약과 Mori 기동/표시 메타데이터를 동기화한다. 동기화 전에는 “예약 준비 중”이며 등록 완료를 주장하지 않는다.
6. 기능 탭에서 확인·수정·실행·일시 중지할 수 있다. 시간대에 맞춰 상단 카드에 나타나며 상세는 공통 템플릿으로 표시된다.
7. 후속 요청 때 Hermes는 Mori에서 내 기능을 다시 조회해 활성 버전을 사용한다.

모든 저장마다 승인 팝업을 요구하지 않는다. 실행에 필요한 정보 부족이나 기존에 허용하지 않은 동작이 추가되는 경우에만 구체적인 내용을 확인한다. 확인/미리보기 화면은 수정 수단이며 불필요한 재승인 흐름으로 만들지 않는다.

### G. 기능이 없는 일반 대화

Hermes가 내 기능을 확인했지만 적합한 기능이 없으면 일반 대화/일회성 작업으로 답한다. 그 이유만으로 새 스킬이나 대시보드 카드를 자동 생성하지 않는다. 사용자가 “이걸 기능으로 만들어줘”라고 요청하거나 허용된 자동 개인화 규칙에 해당하면 별도 기능 생성 흐름으로 이어간다.

## 6. 대화·마이크 공통 흐름

```text
대시보드 채팅 입력 선택 → 대화 패널 확장 → 메시지 전송
대시보드 마이크 선택 → 음성 상호작용 → 녹음 종료/전사 → 같은 대화 패널 확장·전달
                                      ↓
                     내 기능 조회 → 적합한 기능 실행 또는 일반 대화
                                      ↓
                 실제 진행 상태 → 답변/기능 결과 → 대시보드 갱신
```

음성은 전사 후 같은 채팅 파이프라인을 사용한다. 녹음과 전사 단계, agent 처리 단계를 구분한다. 전사 내용을 말풍선에서 볼 수 있고 수정·후속 발화가 가능해야 한다. 텍스트↔마이크 전환으로 대화 ID·입력 초안·진행 작업을 잃거나 같은 요청을 두 번 보내지 않는다. 인식이 실패하거나 내용이 불확실하면 오작동 대신 수정 기회를 제공한다.

대시보드 입력에서 새 대화를 시작할지 마지막 대화를 재개할지의 기본 정책은 미정이다. 대화 탭에서 특정 기록을 열 때는 해당 대화를 명시적으로 이어간다.

## 7. 변경된 결정과 미정 항목

| 항목 | 현재 방향/결정 필요 |
| --- | --- |
| 탭 구성 | 5개 탭으로 확정. 이전 오늘/캘린더/기억·보관함을 최상위 탭으로 둔 설계는 대체 |
| 기본 vs 커스텀 | 기본은 전용 상세/애니메이션, 커스텀은 공통 템플릿 |
| 기능 저장 기준 | Mori에서 조회할 수 있는 기능/스킬 버전이 기준. Hermes 로컬 복사본과 동기화 정책 필요 |
| 입력 필수 값 | 사용자가 모든 필드를 채우는 폼을 강제하지 않음. 실행 가능한 최소 정보만 질문 |
| 결제 | 마이의 목표 범위에 포함. 현재는 관리자 승인 Pro이며 결제 도입 시 전환·기존 승인 계정 정책 미정 |
| 한도 | 기존 무료 비서/위젯 약 3개 제안은 새 기능 개수 한도로 자동 전환하지 않음. 기능·예약·실행 한도 별도 결정 |
| 캐러셀 | 동시 항목 우선순위·표시 구간·자동 넘김 여부·최대 개수 미정. 수동 탐색을 기본 제안 |
| 습관 | 어떤 근거를 얼마나 쌓아 출근 시간을 추론할지, 변경 설명과 자동 개인화 범위 미정 |
| 알림 | 카드/푸시/로컬 알림 채널 정책, 반복·다시 알림·권한 거부 시 처리 결정 필요 |
| 종목/뉴스 | 데이터 제공자, 지연·캐시·갱신 정책, 출처 규격 미정 |
| 커스텀 템플릿 | 초기 블록 종류와 편집 범위·버전 호환·미지원 렌더링 결정 필요 |
| 아이콘 | 이미지 출처/사용 조건·보관·교체 정책, 기본 fallback 자산 준비 |
| 최근 대화 | 대시보드 하단 노출 여부와 항목 수 미정 |

미정 항목이 있다는 이유로 전체 개발을 멈추지 않는다. 공통 기능 정의/결과/표시 계약을 먼저 만들고 기본 주차·메모·알림으로 세로 흐름을 검증한 뒤 뉴스·주가·커스텀 자동화를 확장한다.
