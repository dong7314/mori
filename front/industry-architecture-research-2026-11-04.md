## 1. 이번 조사에서 다시 확인한 결론

당근은 공식 자료에서 네이티브 기반, React 웹뷰와 일부 Lynx 화면을 확인할 수 있다. 당근 앱 전체가 React Native로 구현됐다는 결론은 내리지 않는다. 사용자가 기억하는 RN 채용 공고는 원문을 특정하지 못했으므로 해당 기억을 잘못됐다고 판정하지도 않는다. 특정 팀이나 과거 RN 사용 가능성까지 부정하는 조사도 아니다.

실제 RN과 웹을 함께 운영한 공식 사례는 토스의 2024년 기술 글과 Bluesky의 공개 저장소로 별도 확인했다. 세 회사가 코드를 공유하는 방식은 서로 다르다. Mori는 **기존 PoC의 DOM/CSS 화면을 React 웹으로 옮기고 RN의 한 WebView에서 재사용**하는 현재 방향을 유지한다. 아래의 적용 판단은 Mori의 결정이며 각 회사가 동일하게 운영한다는 주장과 구분한다.

## 2. 조사 방법과 근거의 수명

- 검색 결과로 자료를 찾은 뒤 당근 공식 채용·당근 기술 블로그, 토스 기술 블로그, Bluesky 공식 저장소의 원문을 직접 열어 확인했다.
- 채용 공고는 2026-11-04 실제 열리는 본문을 확인했다. 게시/갱신일이 본문에 없으면 날짜를 추측하지 않는다. 공고가 닫힌 뒤에도 현재 채용 중인 것처럼 재사용하지 않는다.
- 기술 글은 게시 당시의 구현 설명이다. 2024년 토스 구조나 2022년 당근 호스팅을 2026년 전체 시스템의 현재 목록으로 확장하지 않는다.
- 회사·채용 공고별 기술을 섞어 하나의 ‘당근 표준 스택’으로 만들지 않는다. 제3자 채용 복사본·댓글·AI 요약은 기술 선택의 근거에서 제외했다.
- 단순 도입 사실과 성능 수치, 출시/업데이트 정책을 구분한다. 공개 글에 없는 지원 앱 버전 수·강제 업데이트 기준·사용자별 rollout 수치를 추정하지 않는다.

## 4. 토스: Native·RN·WebView의 혼합과 서비스별 배포

[토스가 꿈꾸는 React Native 기술의 미래](https://toss.tech/article/react-native-2024)는 **2024-03-25** 글이다. 본문을 2026-11-04 다시 확인했다. 당시 토스는 네이티브와 RN/WebView를 함께 쓰고, 서비스별 RN 뷰와 공통/서비스 번들을 나눠 운영한다고 설명한다. 별도 배포 플랫폼으로 CDN 게시·일부 사용자 노출을 관리한 사례다.

여기서 참고할 점은 제품 화면과 기기 실행 환경의 배포 수명이 다르다는 사실, 공통 기반과 서비스 책임을 나누는 방식이다. 당시의 자체 번들러·공유 번들·마이크로 프론트엔드는 큰 조직의 플랫폼 투자다. Mori 초기 앱에 같은 배포 엔진을 만들거나 Metro를 교체하는 근거로 쓰지 않는다. ‘웹 배포와 앱 배포를 나눈다’는 목표를 현재 Harbor·k3s와 작은 버전 계약으로 달성한다.

이 글만으로 현재 토스의 모든 화면 구성이나 스토어 build/min-build 정책, RN 원격 업데이트 허용 범위를 확정하지 않는다. 특히 글의 배포 속도를 Mori의 개발/출시 보장 수치로 사용하지 않는다.

## 5. Bluesky: RN 컴포넌트와 React Native Web을 공유하는 대안

[Bluesky 공식 앱 저장소](https://github.com/bluesky-social/social-app)의 README는 웹·iOS·Android용 TypeScript React Native 앱과 React Native Web 서빙을 설명한다. [현재 package.json](https://github.com/bluesky-social/social-app/blob/main/package.json)에서도 Expo의 native/web 실행 스크립트를 확인했다. 확인일은 2026-11-04이며 이 문서는 특정 patch 버전을 그대로 가져오지 않는다.

이 구조는 RN 컴포넌트를 웹에서도 쓰는 방향이다. Mori는 이미 DOM/CSS로 검토한 화면과 입력·카드 확장 동작이 있고 사용자가 React 웹을 직접 개발할 계획이므로 **DOM 웹 + RN WebView**를 선택한다. RN Web을 쓰는 방식이 나쁘다는 뜻이 아니라 공유할 UI의 출발점이 다르다. 소스 공개와 디자인 자산의 사용 권한도 구분하며 다른 서비스의 아이콘·일러스트·상표를 복사하지 않는다.

## 6. 세 패턴과 Mori의 선택

| 패턴 | 화면 재사용 방식 | 장점 | Mori 초기 판단 |
| --- | --- | --- | --- |
| 당근의 공개 혼합 사례 | 네이티브 앱과 웹 화면, 일부 Lynx | 업무/화면별 기술 선택, 독립 웹 운영 | 책임·관측·화면 단위 전환을 참고 |
| 토스의 2024 RN 사례 | native 호스트와 서비스별 RN/WebView | 서비스별 개발/배포와 공통 플랫폼 | 운영 경계 참고, 자체 MFE 플랫폼 복제는 제외 |
| Bluesky RN/RN Web | RN 컴포넌트 중심의 웹·앱 공유 | 하나의 컴포넌트 체계에서 플랫폼 확장 | 기존 DOM PoC를 새 렌더러로 재작성하는 비용이 있어 초기 제외 |
| Mori 채택안 | React DOM 웹을 RN의 주 WebView에서 사용 | PoC UI를 웹으로 이식하고 기기 경계만 RN으로 구현 | 현재 기본안, 실기기/성능 시험 후 필요한 화면만 재검토 |

선택의 핵심은 기술 이름보다 **재사용 범위와 배포 경계**다. React 웹의 HTML 컴포넌트를 RN으로 자동 변환하지 않는다. 공유 패키지는 API 타입/규칙·브리지 스키마·디자인 토큰으로 제한하고 웹 UI와 native 모듈은 각 플랫폼 경계에 둔다. 앱 위젯도 WebView 안의 카드와 별도 구현이다.

## 7. 공개 사례에서 Mori 작업으로 옮길 항목

아래는 조사 사실을 바탕으로 정한 **Mori 적용 계획**이다. 회사 내부 표준이라고 주장하지 않는다.

| 적용 항목 | Mori에서 만들 것 | 완료 증거 |
| --- | --- | --- |
| 같은 제품의 공통 UI | 색/여백/글자/모션 토큰과 버튼·필드·선택·행·상세 외곽 | 같은 상태의 화면을 여러 탭에서 비교하고 접근성 확인 |
| 화면별 책임 | dashboard/schedule/conversations/features/account의 기능 경계 | 도메인 API와 캐시 갱신·상세 이동이 모듈 안에서 추적됨 |
| 탐색의 단일 주체 | 웹 화면 스택·URL과 RN 시스템 back의 책임 계약 | 중첩 picker→채팅→상세→탭 복귀가 한 번씩 처리됨 |
| 작은 host 인터페이스 | handshake·capability·요청 ID·취소/오류·origin 확인 | 지원 안 함·권한 거부·앱 재로드의 자동 검사/실기기 결과 |
| 웹/앱 독립 배포 | 변경 불가능한 웹 release와 서명 앱 build·bridge 호환 범위 | 구/신 앱 × 구/신 웹 시험표와 이전 정상 웹 복귀 |
| 점진적 도입 | 공통 UI→대시보드 fixture→RN 실험→첫 API 흐름 | 각 작업에서 실행 화면·검사·남은 제한 기록 |
| 성능과 복구 | 첫 화면·탭/상세 전환·키보드·SSE 복귀·오류를 같은 시나리오로 측정 | 같은 기기/네트워크의 재현 기록과 변경 전후 비교 |
| 코드 공유 | API client·bridge·design tokens만 workspace 패키지로 시작 | 웹 번들에 RN 모듈, native 번들에 DOM 전용 코드가 섞이지 않음 |

Mori의 첫 기준 동선은 로그인→주차 저장→대시보드 재조회→채팅/SSE→결과 상세다. 전체 화면을 동시에 갈아엎기보다 이 흐름에서 캐시·인증·탐색·키보드·오류 처리를 먼저 확정한다. 이후 일정·기록·문서·기능/예약·뉴스/주가·결제를 같은 기반으로 연결한다.

## 8. 처음부터 복제하지 않을 플랫폼

| 항목 | 초기 제외 이유 | 다시 검토할 계기 |
| --- | --- | --- |
| Lynx·추가 렌더러 | 새 호스트·디자인/접근성·배포·오류 수명이 추가됨 | 실제 WebView 병목이 측정되고 해당 화면의 대안 시험이 통과할 때 |
| 서비스별 독립 RN 번들/MFE | 개발자 1명에게 배포/호환 운영 비용이 큼 | 독립 팀·릴리스가 실제 필요해질 때 |
| 자체 대규모 웹 호스팅 | 기존 k3s/Harbor로 초기 release를 운영할 수 있음 | 다중 팀·대량 release·운영 요구가 명확해질 때 |
| RN JS OTA | 웹 release 교체와 다른 native 호환 수명을 가짐 | 서명·runtime 호환·복귀·스토어 정책 검토를 끝낸 별도 결정 |
| 모든 UI의 RN/RN Web 재작성 | 이미 합의한 DOM/CSS 상호작용 이식 비용 | 웹 재사용보다 native 화면의 이득이 검증될 때 |
| 회사 디자인 시스템 외형 복제 | Mori의 색·타입·카드/상세 요구와 다름 | 동작/접근성 primitive만 평가하고 외형은 Mori 토큰 유지 |

‘당근이 사용한다’는 이유만으로 Stackflow·SEED·vanilla-extract를 함께 설치하지 않는다. 각 후보는 Mori의 라우팅·모션·접근성·실기기 조건과 라이브러리 검토 문서의 채택 기준을 통과해야 한다. 패키지의 유지보수와 호환 버전은 실제 착수 시 고정하고 회사 채용 공고의 조합을 그대로 lockfile로 옮기지 않는다.

## 9. 아직 공개 자료로 확정하지 못한 항목

- 사용자가 보았던 당근 RN 공고의 원문·팀·게시 시기.
- 당근·토스 전체 제품의 현재 화면별 렌더러 비율과 사내 semver/min-build/강제 업데이트 정책 숫자.
- 공개 글 작성 뒤 회사별 내부 플랫폼이 얼마나 달라졌는지.
- Mori에 필요한 실제 warm/cold 시작·키보드/스크롤·브리지·구형 기기의 성능과 최소 OS.
- Mori의 앱 ID·판매 방식·정확한 라이브러리 patch 버전·앱 스토어 인수 결과.

이 미확정 항목 때문에 화면 이식을 멈추지 않는다. 제품 코드·타입/상태/폼/탐색의 상세 작업과 버전/호환 정책은 Mori의 결정으로 기록하고, 실험과 코드가 생기면 근거 커밋과 기기 결과를 추가한다. 회사의 사용 사례와 Mori의 적용 결정을 같은 완료 상태로 표시하지 않는다.
