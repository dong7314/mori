# 기존 PoC를 실제 React 화면으로 옮기는 실행 계획

작성일: 2026-10-06 · 갱신일: 2026-11-03 · 상태: 계획 갱신, 제품 프론트 01~12 구현 시작 전

[전체 계획](../plan.md) · [화면 기획](plan.md) · [React/RN 구조](react-native-webview-plan.md) · [배포 계획](../architecture/app-release-versioning.md)

## 1. 이번 계획의 목표

기존 `poc`의 화면·마스코트·상호작용을 기준으로 `master`에 React 프론트엔드를 만든다. 먼저 브라우저에서 화면을 확인하고 실제 API를 하나씩 연결한 뒤, 같은 화면을 React Native/WebView 앱으로 제공한다. 새로운 디자인을 처음부터 다시 만들기보다 이미 합의한 PoC를 제품 코드로 옮기는 작업이다.

화면 작업은 작게 나누고 각 단계가 끝날 때 실행 주소, 바뀐 화면, 확인한 동작과 남은 제한을 함께 제시한다. 사용자는 결과를 확인한 뒤 다음 단계나 수정 사항을 지정할 수 있다. 이 문서는 실행 순서를 정리한 계획이며 모든 단계가 구현됐다는 기록이 아니다.

### 2026-11-03 상태 판정

화면 기준은 `poc` `8fa4fe4`, 서버 기준은 `master` `6285aba`의 API 0.9.0과 migration `0017_news_refresh_deadline`이다. 초기 10월 6일 계획에서 후속으로 적었던 서버의 예약·사전 기동·개인 runtime·지속 채팅·문서 작업·웹 결제·국내 주식 분봉이 구현됐다. **React 제품 화면·RN 컨테이너·브리지·제품 웹 세션은 아직 없으므로 01~12 완료 표시는 모두 대기**로 둔다. 기존 PoC를 새 백엔드에 연결한 통합 시험도 수행하지 않았다.

API 코드를 새로 만드는 작업과 이미 있는 API에 화면을 연결하는 작업을 구분한다. 상세 범위는 [현재 백엔드 상태](../back/implementation-status-2026-11-03.md), [0.9 화면 대조표](https://github.com/dong7314/mori/blob/6285abac905b242442cceda103c63e18d8900ab3/backend/docs/poc-parity-map-0.9.md), [화면 기준 코드](https://github.com/dong7314/mori/blob/8fa4fe4/src/app-experience.js)를 따른다. 로컬 backend 726개와 Hermes 91개 통과·1개 skip·43 subtest는 서버 검사 결과이며 이 계획의 제품 화면·기기 인수 완료로 합산하지 않는다.

## 4. 단계별 작업 범위와 완료 기준

### 01 — React 기반과 공통 UI

- `frontend/apps/web`에 React/TypeScript/Vite 개발·빌드·타입 검사 환경을 준비한다. 패키지 버전은 착수 시 호환성을 확인하고 고정한다.
- 앱 프레임, 5탭, 상세 진입/뒤로가기, 페이지별 스크롤 보존의 기본 구조를 만든다.
- PoC의 색상·4/8/12/16/24/32px 간격·글꼴·모서리·모션을 공통 토큰으로 정리한다.
- Button, Field, Select, BottomSheet, Card, EmptyState, LoadingState, ErrorState를 필요한 최소 범위로 만든다. 특히 select 모양·여백·키보드 포커스를 통일한다.
- 개발용 fixture와 실제 API transport의 경계를 둔다. 개발용 데이터 선택은 개발 설정에서 하고 마이에 PoC 옵션을 추가하지 않는다.

완료 기준: 브라우저에서 5탭이 이동하고 320/375/768/1280px에서 가로 넘침·하단 가림이 없다. 공통 선택/패널을 키보드로 열고 닫을 수 있으며 모션 감소 설정을 반영한다. 첫 결과는 화면 뼈대와 공통 UI이고 로그인/AI 연결은 아직 아니다.

### 02 — 대시보드 재현

- mori 로고·사용자 정보 진입·날짜/인사, 상단 시간 카드, 아래 기록/문서, 하단 둘러보기/반복하는 부탁 만들기, 채팅/마이크 진입을 옮긴다. 대시보드의 오늘의 약속·최근 대화 중복 섹션은 복원하지 않는다.
- 오른쪽 시간 버튼은 지금/3시간/5시간/24시간을 선택하며 시간대별 가로 목록을 펼친다.
- 주차·뉴스·주가·일정·알림·커스텀의 시각적 카드와 공통 상세 외곽을 만든다. 이 단계의 데이터는 명시적인 개발 fixture다.
- 카드가 0개/1개/여러 개일 때, 결과가 예정/처리 중/실패/오래된 상태일 때를 준비한다. 가짜 미래 결과로 빈 상태를 채우지 않는다.
- 기록과 정리는 분류 탭 없이 최근 최대 5개와 전체 보기로 구성한다. 분류·검색·추가 조회는 전체 기록 화면에서 제공한다. 행 높이·한 줄 말줄임, 시간 범위 선택의 체크 표시와 캐러셀 좌우 버튼을 공통 규격으로 맞춘다.
- 카드에서 상세로 펼쳐지고 같은 카드로 돌아오는 전환 중 내용·아이콘을 중간에 바꾸지 않는다. 하단 입력창 위치는 유지하고 채팅/음성 패널만 위로 확장한다. 모션 감소에서는 같은 탐색 의미를 즉시 전환으로 보존한다.

완료 기준: 기존 PoC와 정보 우선순위·마스코트·간격을 비교할 수 있다. 시간 범위를 바꿔도 실제 시계/예약을 변경하지 않는다. 카드와 하단 입력 영역이 서로 겹치지 않으며 캐러셀·세로 스크롤이 충돌하지 않는다.

### 03 — RN/WebView 최소 실험

- `frontend/apps/mobile`에 iOS/Android 앱을 만들고 02의 웹을 주 WebView 하나로 연다.
- handshake, 지원 capability, safe area, 앱 복귀, 외부 링크, Android 뒤로가기와 iOS 탐색 동작을 확인한다.
- 입력창에 키보드가 올라와도 폼/하단 버튼이 보이는지 확인한다. 마이크 권한 요청은 범위가 작은 실험으로 확인하고 실제 음성 전사는 11에서 연결한다.

완료 기준: 앱 안에서 대시보드와 주차 샘플 상세를 열고 돌아온다. 뒤로가기가 두 번 실행되거나 여백이 중복 적용되지 않는다. 웹을 못 열면 앱 자체의 재시도 화면이 남는다. 스토어 제출은 아직 하지 않는다.

### 04 — 로그인과 마이

- 기존 네이버/카카오 로그인·코드 교환을 재사용하고 [제품 웹 세션/앱 교환 계약](../back/mobile-client-contracts.md)을 구현한다. 초기에는 웹 세션부터, 이어 native 로그인 복귀와 WebView 세션을 연결한다.
- 사용자 정보·정보 수정, 시스템/라이트/다크, Free/유효 Pro 요금제, logout을 연결한다. Pro는 관리자 승인 또는 유효한 결제 기간으로 판정하며 서버 응답의 근거를 사용한다.
- 소셜 키와 callback은 서버/개발자 콘솔에서 설정한다. 키가 없거나 잘못된 경우 화면 안내를 검증하고 실제 로그인 성공으로 처리하지 않는다.

완료 기준: 실제 소셜 계정으로 로그인 → 이름·테마 저장 → 재접속 → logout이 가능하다. 세션 만료·로그인 취소·서버 재시작을 처리하고 다른 계정 로그인 후 이전 데이터가 보이지 않는다. 결제 버튼은 서버의 설정/이용권 응답을 따르며 실제 웹 청구·해지 연결은 10에서 검증한다. 운영 키가 없으면 미설정을 표시하고 API가 없는 것으로 안내하지 않는다.

### 05 — 주차와 대시보드 API

- 주차 직접 입력을 `POST /v1/parking-records`와 연결하고 최신 위치를 조회한다.
- 출근용/외부, 상시/지정 시간, 요일·시간대·표시 기간과 미리보기를 반영한다.
- 대시보드는 `/v1/dashboard?hours=0|3|5|24`, 기록은 `/v1/library`를 사용한다. 순서/표시 구간은 서버 응답을 따른다.
- 저장 후 최신 위치·대시보드 캐시를 갱신한다. 상시 기록의 `show_until=null`을 처리한다.
- PoC 로컬 `always` 중 ‘기능 탭에서만 보기’는 서버 `manual`로 매핑한다. 서버의 명시적 `always`는 다음 위치 저장까지 대시보드에 표시하는 별도 의미다. 두 값을 그대로 일치시켜 원치 않는 시간 카드를 만들지 않는다.

완료 기준: B3/B16을 저장하고 새로고침해도 같은 계정에 남는다. 다음 위치 저장으로 최신 카드가 바뀌고 같은 요청 재전송으로 중복되지 않는다. 시간 지정은 카드 표시 설정이며 푸시 예약 성공으로 안내하지 않는다.

### 06 — 대화 목록과 실제 채팅

- 대시보드에서 올라오는 채팅 패널과 대화 탭에 같은 메시지/대화 상태를 사용한다.
- 대화 생성·목록·검색·이름·고정·삭제와 기존 대화 재개를 연결한다.
- `POST /v1/conversations/{id}/runs`의 202와 상태/이벤트 주소를 보관하고 `GET .../events`로 실제 단계·최종 완성 답변을 관찰한다. 기존 POST `/messages`는 호환 경로다.
- 이벤트 ID와 `Last-Event-ID`/`after`로 재생하고 기본 25초 관찰 종료 뒤 재연결한다. 패널 닫기·관찰 종료는 취소로 처리하지 않으며 별도 취소 버튼으로 `/cancel`을 요청한다.
- 저장된 `result_refs.kind/detail_url`로 주차/일정/메모/뉴스/주가/기능/문서 작업에 이동하고 연결 종료 시 run 조회로 상태를 확인한다. 대화 그룹에는 `last_activity_at`, 미리보기에는 `last_message`를 사용한다.

완료 기준: 자연어 주차 요청의 실제 저장 결과가 대시보드에 반영되고 “내 차 어디야?”를 같은 대화에서 이어갈 수 있다. HTTP 200만으로 성공 표시하지 않으며 가짜 스킬 탐색/모델 생각 문구를 만들지 않는다. 같은 요청의 이중 전송과 스트림 종료 후 무한 스피너를 막는다.

실제 기능 인수에는 Hermes 연결과 활성 채팅 worker가 필요하다. 그 전에는 SSE fixture로 UI를 검증할 수 있지만 실제 AI 통합 완료로 기록하지 않는다. 서버의 지속 큐·이벤트 저장은 구현됐으며 앱의 백그라운드·재시작 복구는 아직 제품 연결/실기기 인수가 필요하다. 명시적 취소는 이미 완료된 저장을 되돌리는 기능이 아니다.

### 07 — 스케줄

- 월/주/일 전환, 선택 날짜, 일정 상세와 직접 입력/수정/삭제/복원을 연결한다.
- 종일·시간 지정·장소·메모, 겹치는 일정과 날짜를 넘는 일정을 표현한다.
- 직접 등록과 AI 등록이 같은 데이터를 쓰며 저장 후 달력·대시보드를 함께 갱신한다.

완료 기준: 캘린더의 추가 버튼이 채팅으로 이동하지 않는다. 자정 경계와 종료일 제외 규칙, revision 충돌을 처리하며 월/주/일 모두 같은 기록을 보여준다. 반복 약속·실제 기기 알림을 지원 완료로 노출하지 않는다.

### 08 — 메모와 기록 목록

- 메모 작성/수정/검색/삭제/복원, 상세, 대시보드 최근 기록과 전체 목록을 연결한다.
- 페이지 추가 조회·빈 목록·긴 본문을 처리하고 수정 충돌에는 현재 서버 값을 다시 확인할 수 있게 한다.
- 대시보드 최근 5개와 전체 기록의 공통 아이템을 사용한다. 유형별 아이콘·파일명/바이트·체크 개수를 표시하고 목록의 미리보기와 상세 원문을 구분한다. 삭제·복원만으로 메모의 마지막 내용 저장 시각을 오늘로 바꾸지 않는다.

완료 기준: 직접/채팅 작성 메모를 같은 목록에서 열고 수정·재조회할 수 있다. 삭제 시 최근 기록에서도 빠지고 복원 시 다시 보인다. 대화 삭제를 메모 삭제로 처리하지 않는다.

### 09 — 파일과 문서 작업

- 기존 TXT/MD/CSV 원문 API와 새 바이너리 파일/문서 작업을 구분한다. 파일 선택 → 원본 바이트 업로드(`/v1/files`) → 작업 접수(`/v1/document-jobs`) → 상태 조회 → 완료 파일 다운로드를 연결한다.
- DOCX/XLSX 생성과 제한된 편집, PDF 읽기·생성·페이지 조작, HWP/HWPX 읽기의 지원 범위를 화면에 반영한다. 원본 HWP 편집·OCR·수식 재계산을 지원한다고 표시하지 않는다.
- 목록은 메타데이터만 사용하고 상세에서 원문/읽기 결과를 가져와 제한된 미리보기를 제공한다. 파서의 잘림 표시와 작업 실패·취소·새 작업으로 재시도를 구분한다.
- 개발 fixture용 IndexedDB와 실제 서버 문서를 섞지 않는다. 10,000,000바이트 원문 제한과 전송 크기 제한을 구분한다.

완료 기준: 10MB 경계·초과·한글/줄바꿈·새로고침 후 상세·다운로드를 확인한다. 업로드는 multipart가 아닌 원본 바이트이며 전체 quota와 휴지통을 반영한다. 파일 보관·작업 접수·완료 파일을 구분하고 원본은 덮어쓰지 않는다. 채팅 첨부는 본인 문서/파일 ID를 명시하며 삭제·취소·권한 상실 시 잘못된 완료 표시가 없다. 실제 정상 HWP/HWPX 원본 전체 및 Linux 이미지 검증은 운영 인수에서 따로 확인한다.

### 10 — 기능·뉴스·주가·알림과 웹 결제

- 기본 기능/내 기능 목록, 설명·work·선택 시간 설정·기본 아이콘·상태를 실제 계약에 맞춰 연결한다.
- 커스텀 생성/수정·미리보기·버전·중지와 결과 목록/상세를 구현한다. title/description/contents 등을 전부 필수 입력으로 강요하지 않는다.
- “지금 실행”은 기존 채팅에 feature_id를 전달한다. 현행 텍스트 결과부터 표시하고 다양한 표/이미지/파일 블록은 서버 계약 확장에 맞춰 추가한다.
- 알림 목표 시각의 카운트다운·연장·취소를 연결하되 전달 미설정 상태를 구분한다.
- 사용자 기능은 기본 `reply` 권한이며 저장 동작은 사용자가 명시적으로 선택한다. 중지/초안 조회, 실행·재개·설정 변경을 구분하고 모델이 권한을 늘리는 UI를 만들지 않는다.
- 뉴스 주제/수집 시각과 수동 재수집, 요약/출처·마지막 성공·오래된 결과를 연결한다. 요약 근거는 검색 발췌이며 기사 전체 열람으로 표현하지 않는다.
- 주가 종목·예약 설정과 국내 주식 당일 1분봉, 기타 일봉·종가를 구분한다. `interval`, `price_kind`, `as_of`, 거래일·빈 결과를 표시하고 종가를 장중 현재가로 꾸미지 않는다. 장전·휴장·특수 장시간의 지원 한계는 실제 응답/서버 계약을 따른다.
- 마이의 웹 Toss 결제·주문 확인·구독 상태·기간 말 해지/해지 철회를 연결한다. UI가 가격/성공을 임의로 확정하지 않고 제공자 테스트 환경에서 승인·실패·중복·응답 유실을 확인한다. 스토어 구매·즉시 환불 버튼은 현행 API가 아니다.

완료 기준: 정의 저장·예약 등록·실제 회차 완료를 구분하고 과거 결과는 당시 버전을 유지한다. 뉴스·시세는 실제 설정된 제공자의 자료/시각으로 확인하고 예약은 Mori DB/worker의 회차 조회·취소 상태를 사용한다. 알림 진행률은 `started_at/target_at` 기준으로 재접속 후 복원한다. 해당 환경의 provider/worker가 없으면 준비 중/미연결 상태를 표시하며 예시 숫자나 결제 성공을 만들지 않는다.

### 11 — 음성 입력

- RN 녹음 시작/중지/취소·권한·임시 파일 처리를 구현하고 기존 `/v1/speech/transcriptions`와 실제 전사 제공자 설정을 연결한다.
- 녹음 파형 → 전사 → 인식 문장 확인/수정 → 같은 대화 전송 → SSE 응답을 구성한다. 전사 API는 자동 채팅 제출을 수행하지 않는다.
- 텍스트/마이크 전환 시 대화 ID와 초안을 유지하고 전사 실패는 수정/재녹음으로 복구한다.

완료 기준: 실제 음성을 녹음해 요청하고 응답을 받는다. 권한 거부·앱 중단·취소·중복 전송을 확인한다. 브라우저 음성 체험을 native 전사 구현 완료로 계산하지 않는다.

### 12 — 기기 기능과 테스트 배포

한 작업으로 묶지 않고 아래 순서로 각각 진행한다.

1. 앱 버전/client-config와 staging 웹 배포, 로그인·파일·SSE 실기기 통합을 확인한다.
2. 기기 등록·해제·권한 상태와 기본 알림 전달을 구현한다. 기존 목표 시각 저장과 실제 전달을 연결한다.
3. 주차/일정 위젯과 snapshot 조회·캐시·딥링크를 구현한다. OS 위젯의 갱신 시각은 보장하지 않는다.
4. 구현된 Mori DB 예약·prewarm·worker를 실제 환경에 배포하고 사용자별 콜드 스타트·결과 반영을 연결 검증한다. Hermes cron 동기화를 별도 구현할 단계로 되돌리지 않으며 앱 timer로 대체하지 않는다.
5. TestFlight/Play 내부 테스트, 구/신 앱 호환과 웹 복귀를 확인한 후 스토어 출시 단계로 간다.

완료 기준: 앱이 닫힌 상태에서 가능한 기기 동작과 제한을 실측하고, 계정 전환 시 이전 사용자 알림/위젯 데이터가 남지 않는다. 새 native 기능은 앱 build로 배포하고 웹만 바꿔 설치된 앱 기능이 생겼다고 가정하지 않는다.

서버의 Web Push와 native Push를 구분한다. Web Push용 service worker 예시는 이미 있지만 APNs/FCM 기기 등록·해제·위젯 snapshot·client-config·앱 구매 검증은 아직 별도 작업이다. RN OTA를 채택하더라도 native 모듈/권한 변경을 웹 배포처럼 전달할 수 있다고 가정하지 않고 구/신 앱 호환과 복귀 절차를 먼저 확인한다.

## 5. 매 단계의 작업 방식

1. 이번 단계의 화면과 직접 눌러 볼 시나리오를 정한다.
2. 해당 화면·API 어댑터를 구현하고 공통 컴포넌트 변경은 사용하는 화면에 함께 반영한다.
3. 의미 있는 로직/연결 검증과 모바일 화면 확인을 수행한다. 단순 스타일 변경마다 구현을 복제한 테스트를 늘리지 않는다.
4. 사용자가 확인할 주소와 결과를 제공하고, 실제 연결/fixture/미구현을 구분한다.
5. 피드백을 반영한 뒤 완료 상태·관련 커밋·검증 범위를 이 계획에 기록한다.

API 변경이 필요하면 입력·응답·오류와 OpenAPI를 먼저 맞춘다. 변경 없는 API를 화면마다 새로 만들지 않는다. 각 기능의 완료에는 저장 후 재조회와 빈 상태/실패/재시도를 포함한다.
