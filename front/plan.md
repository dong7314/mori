# Front — 사용자 경험·화면 설계

[전체 계획으로 돌아가기](../plan.md)

갱신일: 2026-09-17 · 앱 우선 방향, 현재 PoC와 실행 준비 대기 UX 반영

실제 서비스 프론트엔드와 모바일 앱·위젯 구현은 사용자가 담당한다. AI는 사용자가 요청한 범위의 `poc` 화면과 API 계약·예시 데이터를 준비한다. **제품은 휴대폰 앱을 기준으로 개발하고 태블릿까지 지원한다. 휴대폰·태블릿 모두 세로와 가로 화면을 검증하며, 독립 웹/데스크톱 웹 제공은 현재 범위에서 제외한다.** 인앱 UI는 React와 WebView 조합을 후보로 유지하고, 녹음·권한·알림·위젯 등 기기 기능은 네이티브 계층으로 연결한다. 앱 컨테이너 기술은 아직 확정하지 않았다.

## 1. 화면의 기본 원칙

- 첫 화면에서 오늘 필요한 정보와 바로 실행할 수 있는 버튼이 보인다.
- 큰 버튼과 짧고 구체적인 문구를 사용한다. ‘에이전트’, ‘스킬’, ‘Pod’ 같은 내부 용어를 주요 사용 흐름에 노출하지 않는다.
- 대화 입력을 잘하지 못해도 ‘주차 기억하기’, ‘일정 추가’로 시작할 수 있다.
- 행동 뒤에는 “지하 3층 B12, 기억했어요”, “토요일 오후 6시 일정을 등록했어요”처럼 결과를 알려준다.
- 음성 인식이 잘못되면 다시 처음부터 말하지 않고 텍스트나 선택 버튼으로 고칠 수 있다.
- 자주 쓰는 기능이 눈에 잘 띄되, 매번 화면의 모든 버튼 위치가 바뀌지는 않는다.
- 글자 확대, 스크린리더, 충분한 터치 영역과 대비를 고려한다. 색상·아이콘만으로 의미를 전달하지 않는다.

## 2. 첫 화면: 앱 안의 오늘

첫 화면은 한 번에 많은 카드를 펼친 웹 대시보드가 아니라 **다음에 챙길 일 → 바로 맡길 일 → 저장된 기억** 순서다.

```text
좋은 아침이에요                       알림 · 설정

[ 다음 일정 또는 지금 필요한 한 가지 ]
  날짜·시간 / 제목 / 장소 / 자세히 보기

무엇을 도와드릴까요?
  주차 위치 기억하기
  코스피 브리핑 받기
  Excel 파일 정리하기

모리가 기억하는 것
  마지막 주차 위치 / 등록한 반복 브리핑

[ 모리에게 부탁하기       마이크 ]
  오늘        대화        캘린더        보관함
```

기본 화면에는 작업 시작점 세 개와 다음 일정 하나를 먼저 보여준다. 여행·그 밖의 요청은 대화에서 시작할 수 있다. 말하기·글쓰기 진입점과 최상위 메뉴의 위치는 안정적으로 유지한다. 저장된 기억과 결과의 세부 내용은 보관함이나 상세 화면에서 확인한다.

카드에는 저장·갱신 시각과 유효 기간을 표시한다. 주차 정보는 언제 기록했는지 알 수 있어야 한다. 자동으로 배운 기능은 왜 보여주는지 짧게 설명하고 수정·중지할 수 있게 한다. 정확한 홈 구성은 사용자 검토로 조정한다.

## 3. 주요 화면과 책임

| 화면 | 사용자가 하는 일 | 필요한 서버 데이터 |
| --- | --- | --- |
| 오늘 | 다음 일정 확인, 주차·정기 브리핑·Excel 작업 시작, 저장된 기억 조회 | 다음 일정, 최근 기록, 반복 기능·작업 상태 |
| 음성 입력 | 녹음·중지·전사 확인·오류 수정 | 전사 결과, 해석 상태, 필요한 추가 질문 |
| 일정 추가/상세 | 등록 결과 확인, 시간·장소 수정, 취소 | 구조화된 일정, 시간대, 알림, 저장 상태 |
| 캘린더 | 일/주/월 일정 확인 | 기간별 일정과 외부 연동 상태 |
| 보관함 | 주차·메모·결과물 찾기, 수정·삭제 | 개인 기록과 최신/과거 구분 |
| 자동으로 챙기는 일 | 반복 시간 변경, 자동화 중지 | 규칙, 마지막 실행, 다음 실행, 허용 범위 |
| 여행 계획/결과 | 조건 입력, 진행 확인, 파일 열기 | 작업 상태, 일정표, 출처, 파일 링크 |
| 일반 대화 | 자유 질문과 후속 대화 | 대화, 작업 카드, 스트리밍 응답 |
| 승인 대기/상세 | 에이전트가 제안한 작업의 내용 확인·승인·거절 | 작업 내용과 버전, 요청자, 만료 시각, 최종 처리 상태 |
| 비서·위젯 관리 | 비서 역할·이름, 위젯 표시 방식 등록·수정, 한도 확인 | Assistant·WidgetConfig, 기기 설치 참조, 등록 개수·정책 버전 |
| 파일 작업 | Excel 첨부·업로드·열/기간 확인, 변경 미리보기·결과 저장 | upload_id, 구조·변환 명세, run_id, 원본/결과 Artifact·만료 |
| 내 설정 | 권한, 자동 개인화, 계정·연동·요금제 관리 | 사용자 설정, 연동 및 전용 환경 준비 상태 |

‘스스로 배운 스킬’은 일반 사용자에게 ‘자동으로 챙기는 일’이나 ‘배운 방식’으로 설명한다. 상세 기술 정보는 관리·개발 화면에서만 보여준다.

## 4. 버튼·음성 공통 흐름

```text
버튼 또는 말하기
  → 필요한 입력 받기
  → 처리 중 표시
  → 정보가 충분하면 실행 / 부족하면 짧게 확인
  → 결과 카드
  → 수정·취소·다음 행동
```

### 주차 기억하기

‘주차 기억하기’ 버튼은 이미 작업 종류를 전달하므로 사용자는 “지하 3층 B12”만 말해도 된다. 저장 후 최신 주차 카드가 갱신된다. “B12가 아니라 B21”이라는 후속 발화는 직전 작업과 연결한다.

‘차 어디 있지?’는 기록 조회다. 최신 기록이 없으면 “아직 주차 위치를 기억한 게 없어요”와 기록 버튼을 보여준다. 오래된 기록을 새 정보처럼 단정하지 않는다.

### 일정 추가

캘린더의 일정 추가는 대화로 이동하지 않고 입력 폼을 연다. 선택한 날짜를 기본값으로 제공하고 저장 후 해당 날짜의 목록에서 확인한다. 말로 등록하는 흐름은 대화에서 별도로 제공하며 결과 모델은 공유한다.

필수 정보가 분명하면 즉시 등록하고 수정·취소 수단을 제공한다. 시간이 애매하면 “오후 6시로 할까요?”처럼 짧은 질문이나 선택지를 보여준다. 필요하지 않은 상세 필드를 한꺼번에 요구하지 않는다.

외부 캘린더 연동 시에는 내부 저장 성공과 외부 동기화 성공을 나눠 표시한다. 연결이 끊겨도 등록 여부를 혼동하지 않게 한다.

### 여행 계획

조건을 한 번에 말하거나 필요한 항목만 단계별로 채운다. 오래 걸리는 검색·파일 생성은 앱을 닫아도 이어지는 작업으로 취급한다. 결과 화면에는 요약 일정, 출처, 확인 시점, 파일 열기·다운로드를 제공한다.

## 5. 상태와 실패 경험

| 상태 | 화면 예시 | 가능한 행동 |
| --- | --- | --- |
| 입력 전 | “무엇을 기억할까요?” | 녹음 또는 텍스트 |
| 녹음 중 | 녹음 시간과 명확한 중지 버튼 | 중지·취소 |
| 음성 해석 중 | “말씀하신 내용을 확인하고 있어요” | 취소 |
| 정보 부족 | “몇 시 약속인가요?” | 선택 또는 다시 말하기 |
| 비서 준비 중 | “개인 비서를 준비하고 있어요. 부탁하신 내용은 저장했어요.” | 기다리기·다른 화면으로 이동·취소 요청 |
| 이용 대기 | “요청이 몰려 잠시 기다리고 있어요.” | 작업 상태 확인·취소 요청 |
| 실행 중/대기 중 | “일정을 등록하고 있어요” 또는 “잠시 기다리고 있어요” | 상태 확인·취소 요청 |
| 완료 | 저장된 위치·일정을 보여주는 결과 카드 | 수정·되돌리기 |
| 실패 | “저장하지 못했어요. 다시 시도해 주세요” | 입력 유지·재시도 |
| 오프라인 | 마지막 받은 정보와 갱신 시각 | 재연결 후 갱신 |

서버가 저장 성공을 확인하기 전에 완료 문구를 보여주지 않는다. 취소 요청을 보냈다고 이미 완료된 외부 작업이 취소된 것으로 표시하지 않는다. 지원되는 작업은 실제 취소/되돌리기 결과를 확인해 갱신한다.

마이크 권한을 거부해도 텍스트 입력과 버튼으로 사용할 수 있다. 백그라운드 상시 녹음은 초기 범위가 아니다. 재전송할 음성 임시 파일이 생기는 경우 사용자가 상태를 알 수 있게 하고 전송·취소 후 보관 정책에 따라 정리한다.

### 유휴 상태에서 다시 부탁할 때

개인 비서의 실행 환경이 쉬고 있어도 앱의 일정·주차·저장된 결과는 바로 조회할 수 있다. 사용자는 Pod를 직접 켜지 않는다. AI가 필요한 일을 맡기면 서버가 자동으로 준비하고, 화면에는 입력과 작업 ID를 유지한 채 대기 이유를 보여준다.

- `run.status=queued`와 `wait_reason=agent_starting`을 실행 준비 안내로, `capacity`를 요청량에 따른 대기로 구분한다. 준비 완료와 실제 작업 완료를 혼동하지 않는다.
- 근거 없는 남은 초·가짜 진행률을 표시하지 않는다. 요청 접수 전 저장 실패와 접수 후 기동 실패를 구분한다.
- 준비 중 앱을 닫거나 다른 화면으로 이동해도 같은 `run_id`로 복구한다. 다시 열거나 재연결했다고 새 요청을 만들지 않는다.
- 기동 실패·기한 초과 시 입력을 보존하고 서버가 허용하는 재시도를 제공한다. 취소 접수와 실제 취소 완료는 구분한다.
- 예정된 브리핑은 서버가 미리 준비한다. 늦어진 경우 예정 시각·실제 처리 상태·자료 기준 시각을 표시한다. 상시 실행이나 즉시 응답을 유료 설명으로 약속하지 않는다.

상태 계약은 [백엔드 실행 수명주기](../back/plan.md#실행-환경의-수명주기와-업무-작업)를 따른다. UI에 `sleeping`, `Pod`, `cold start` 등의 내부 용어를 그대로 노출하지 않는다.

## 6. 개인화와 자동 스킬의 UX

반복 행동에서 스킬을 생성·저장하는 작업 자체로 매번 확인창을 띄우지 않는다. 이미 허용한 동작 안에서 자동화를 개선하고, “아침에 주차 위치를 챙겨드리고 있어요”와 중지·시간 변경 버튼으로 통제권을 제공한다.

사용자가 자동 개인화를 끄면 반복 패턴에 따른 새 카드 배치와 자동 활성화를 중지한다. 명시적으로 등록한 일정·반복 규칙을 함께 끌지는 별도로 설명하고 선택하게 한다.

처음 허용하지 않은 외부 캘린더 쓰기, 외부 전송, 유료 API 사용 등으로 실행 범위가 넓어질 때는 변경 내용을 설명한다. 일상적인 저장과 조회에 매번 동의를 요구하는 UX는 만들지 않는다.

### 비서·위젯 관리와 요금제

무료·유료 모두 기본 기능은 같다. 무료는 비서·위젯 각각 약 3개, 유료는 등록 개수 제한 없음이 현재 방향이며 정확한 한도와 집계는 미정이다. 실제 숫자는 서버 `entitlements` 응답을 사용한다. 등록한 논리적 비서의 수와 실행 중인 Pod 수를 같은 개념으로 안내하지 않는다.

기본 비서 포함 여부, 중지/보관 항목, 여러 기기의 같은 위젯 집계는 계약 확정 후 문구를 맞춘다. 앱에서 위젯 구성을 저장하는 것과 OS 홈 화면에 설치하는 단계도 구분한다. 대시보드의 자동 카드 내용 갱신을 새 위젯 추가로 안내하지 않는다.

한도가 찼을 때는 현재 개수·가능한 정리 방법을 보여주고 기존 항목을 임의로 대체하지 않는다. 자동으로 배운 기능이 새 등록을 필요로 하면 미활성 제안과 선택지를 제공한다. 요금제를 낮춰도 기존 데이터가 즉시 삭제되는 화면을 만들지 않으며, 초과 항목의 이용·유예 정책은 결정 후 서버와 동일하게 표시한다.

## 7. 앱 대시보드 카드와 휴대폰 위젯

앱 안의 카드는 앱 실행 중 바로 갱신할 수 있다. 휴대폰 홈 화면 위젯은 운영체제에서 별도로 구현하고 사용자가 추가해야 한다. PoC의 앱 내 카드와 시간대 미리보기는 실제 홈 화면 위젯과 구분한다.

최종 위젯은 아침의 주차 위치, 약속 전 일정, 여행 중 오늘 계획처럼 시간에 맞춰 카드 내용을 바꾸는 방식을 목표로 한다. 표시 구간과 다음 갱신 권장 시각을 서버에서 내려주고, 기기는 사전에 받은 데이터로 가능한 시간 전환을 준비한다.

Apple WidgetKit은 갱신 예산과 시스템 판단을 사용한다. Android의 주기 갱신도 최소 주기·절전 정책 등의 영향을 받는다. 따라서 ‘매일 정확히 07:30에 서버가 위젯을 강제로 바꾼다’고 보장하지 않는다. [Apple 위젯 갱신](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date), [Android 위젯 갱신](https://developer.android.com/develop/ui/views/appwidgets/advanced).

기기 알림은 위젯 갱신과 별도 경로로 설계하되, 알림 역시 기기 권한·절전·네트워크의 영향을 고려한다. 시간에 민감한 로컬 알림을 사용할지는 플랫폼 결정 후 검증한다.

위젯에는 마지막 갱신·기록 시각을 표시하고, 눌렀을 때 관련 상세 화면으로 이동한다. 공개된 홈/잠금 화면에서 일정 장소나 주차 정보를 감출 수 있게 한다. 로그아웃·계정 변경 때 이전 계정의 캐시를 제거한다.

## 8. PoC 범위와 현재 구현

현재 비교 기준은 `poc`의 `28f8205`다. 초기 HTML·vanilla JavaScript·SCSS 시안(`1725fcd`)에 대화·개인화 흐름을 더하고, 캘린더 직접 추가(`f295729`), 폰트·여백·모션(`0de8d70`), 앱형 화면(`28f8205`)으로 발전했다. 실제 제품은 React 인앱 UI·앱 컨테이너·백엔드에서 별도로 구현한다.

| 항목 | 현재 PoC | 남은 제품 검증 |

`poc/README.md`의 검토 크기는 390×844, 844×390, 768×1024, 1024×768이다. 이는 브라우저 레이아웃 검토 기록이며 실제 기기 검증이 아니다. 이번 문서 정리는 해당 커밋의 소스와 README를 기준으로 했고 화면을 새로 테스트한 기록으로 취급하지 않는다.

후속 PoC에서는 출근길 주차 등 시간별 최우선 카드의 앱형 홈 반영, 실행 준비·실패·오프라인 복구, 실제 업로드를 가정한 파일 상태, 등록 한도, 카드 고정·숨기기를 검토한다. 현재 내부 상태는 확정 API가 아니며 계약 구체화 후 요청·응답·오류를 맞춘다. PoC를 `master`에 적용할 범위는 사용자 검토로 결정한다.

## 9. 프론트·백엔드 인수 기준

- API 문서에 요청/응답, 인증, 오류, 날짜·시간대, 페이지 처리 방식이 정의되어 있다.
- 카드 데이터는 텍스트만이 아니라 종류·작업 ID·행동·표시 기간을 구조화해 제공한다.
- 실행 준비·용량 대기·업무 실행 상태를 구분하고, 새로고침과 앱 재시작 후에도 같은 작업 ID로 복구할 수 있다.
- 기본 버튼으로 시작한 작업과 자유 음성으로 시작한 작업이 같은 결과 모델을 사용한다.
- 사용자가 제공한 대상 기기에서 글자 확대·터치·마이크·알림·위젯 동작을 확인한다.
- 앱에 익숙하지 않은 사용자를 포함해 주차 기록→조회, 일정 등록→확인을 설명 없이 완료하는지 관찰한다.
- 준비 중 취소·재시도·앱 종료·후속 승인에도 입력과 결과가 다른 대화에 섞이지 않는다.
- Excel 원본/결과와 변경 요약·만료·실패가 구분되고, 무료/유료 한도 안내는 서버 정책과 일치한다.

React 인앱 UI의 빌드 도구와 앱 컨테이너는 구현 전 선택한다. 브라우저는 개발·PoC 미리보기에 사용하며, 제품 검증은 실제 휴대폰·태블릿의 네 방향과 기기 기능을 기준으로 한다.

## 10. 휴대폰·태블릿 앱 우선 설계

### 제품 화면과 탐색

- 휴대폰 앱을 기준으로 화면을 설계하고 태블릿을 지원한다. 휴대폰·태블릿의 세로/가로 네 배치를 각각 확인한다.
- 오늘 화면은 다음 일정과 지금 맡길 수 있는 일에 집중한다. 주차 기억, 코스피 정기 브리핑, Excel 정리의 진입점을 먼저 보여준다. 대화·캘린더·보관함은 안정적인 최상위 메뉴로 둔다.
- 휴대폰 세로에서는 하단 탭과 손이 닿기 쉬운 말하기·글쓰기 진입점을 사용한다. 휴대폰 가로에서는 짧은 높이를 고려해 콘텐츠와 고정 입력 영역이 서로 가리지 않게 한다.
- 태블릿 세로·가로에서는 같은 콘텐츠 순서를 유지하면서 두 열과 측면 탐색을 활용한다. 화면이 넓다는 이유만으로 홈에 모든 카드를 펼쳐 놓지 않는다.
- 안전 영역, 글자 확대, 키보드, 회전, 터치 영역과 스크롤 복원을 실제 기기에서 확인한다. OS 상태 표시줄을 웹 화면에 가짜로 그리지 않는다.

### 인앱 UI와 네이티브 계층

React로 작성하는 인앱 화면을 WebView에서 실행하는 방향을 후보로 유지한다. 이것은 독립 웹이나 PWA 출시를 뜻하지 않는다. 브라우저 실행은 개발·PoC 미리보기와 제한된 확인 용도다. 특정 화면의 성능·기기 연동 요구를 WebView로 충족하기 어렵다면 해당 화면의 네이티브 구현을 검토한다.

| 영역 | 담당 |
| --- | --- |
| React 인앱 UI | 오늘·대화·캘린더·보관함, 결과 카드, 파일·반복 기능 관리, 인증된 Mori API 호출 |
| 앱 컨테이너·브리지 | 로그인 연결, 마이크·권한, 파일 저장·공유, 뒤로 가기·딥링크, 기기 안전 영역과 앱 수명주기 |
| OS 기능 | 홈 화면 위젯, 푸시·예약 알림, 알림에서 앱 진입·승인 응답 |
| Mori 백엔드 | 계정별 데이터·권한, 예약 실행, 검색·파일 결과, 알림·위젯 데이터 계약 |

OS 홈 화면 위젯에는 React 화면을 그대로 넣지 않는다. 위젯은 별도 OS 구현과 데이터 전달 경로가 필요하며, WebView가 닫혀 있어도 마지막으로 받은 정보를 표시할 수 있어야 한다. 서버 작업과 알림·위젯 갱신은 앱 실행 여부와 분리한다.

### 앱 컨테이너와 브리지 검증

| 후보 | 검증할 점 |
| --- | --- |
| Capacitor | React 화면 포함·갱신, 마이크·파일·알림 플러그인, iOS/Android 위젯 확장과 인증 연결 |
| React Native + WebView | 브리지·화면 이동·키보드·알림 연결, 네이티브 위젯 추가, 필요한 화면만 네이티브로 확장 |

앱에 화면 파일을 포함할지 서버 URL에서 가져올지, 지원 OS와 버전, Expo 사용 여부는 실제 기기 검증 후 결정한다. 브리지는 필요한 기능부터 좁게 정의하고 요청 ID·결과·오류를 연결한다. 앱/WebView 버전이 다를 때 기능 감지와 업데이트 안내를 제공한다. 외부 페이지에는 앱 브리지를 노출하지 않으며, 서버는 매 요청의 사용자 권한을 검증한다.

알림을 눌러 진입할 때는 로그인·WebView 준비 후 정확한 작업 화면을 연다. 최종 승인·거절·만료와 중복 실행 방지는 서버가 판단한다. 마이크·알림 권한 거절이나 파일 저장 실패에서는 다음 행동을 안내한다.

### 권장 진행 순서와 인수 기준

1. `poc`에서 앱형 오늘·대화·캘린더·보관함과 대표 작업을 휴대폰·태블릿 네 방향으로 검토한다. 이 단계의 브라우저 화면은 시뮬레이션이다.
2. 후보 컨테이너에서 로그인, 녹음, 파일 선택·저장, 뒤로 가기, 위젯 1개, 예약 알림 1개, 알림 진입을 실제 기기로 확인한다.
3. 컨테이너·화면 파일 제공 방식·지원 OS·브리지 계약을 결정하고 `plan`에 근거를 기록한다.
4. `master`에서 앱 컨테이너와 인앱 UI, 브리지, 필요한 OS 위젯·알림 기능을 구현한다.
5. 휴대폰·태블릿 세로/가로, 앱 재시작·오프라인 복구·계정 전환·구버전 앱에서 세 대표 사례를 검증한다.

인수 시에는 주차 기록→위젯 조회, 정기 브리핑 등록→실행 결과, Excel 첨부→정리한 파일 전달이 실제 데이터로 이어져야 한다. 글자 확대·키보드·안전 영역·회전으로 주요 버튼과 결과가 가려지지 않아야 한다. 앱이 종료된 뒤에도 서버 작업·알림·위젯 데이터가 정확한 계정과 작업에 연결되어야 한다.
